### Fixed — `cifix` post-merge: real CI run exposed a 4th bug the review loop missed (`persist-credentials`/extraheader conflict)
The first real, human-triggered CI run after `cifix` shipped got past `Checkout` for the first time since 2026-09-01, then failed one step later at the "Init adr submodule" step: `git ls-remote https://github.com/mohannadrabie/adr.git` returned `remote: Repository not found`, even with a verified-working `ADR_REPO_PAT` (independently confirmed by the human running the identical `ls-remote` locally with the same token — success, correct ref list, matching the pinned SHA). **Root cause, reproduced directly, not assumed:** `actions/checkout`'s default `persist-credentials: true` writes a *local* `http.https://github.com/.extraheader` config entry into `thoth`'s own checked-out `.git/config`, carrying the default `GITHUB_TOKEN`. Git's `http.<url>.extraheader` matching strips userinfo before comparing URLs, so that leftover header still applies to the standalone `git ls-remote` call above (Issue #127's gitlink-reachability precheck, which runs directly in `thoth`'s own checkout context, not inside the submodule) — alongside the `ADR_REPO_PAT`-embedded credential from our own `GIT_CONFIG_*`-scoped `insteadOf` rewrite. GitHub ends up authenticating with the wrong (default) token, which has zero access to the private `adr` repo. Reproduced in isolation: a bogus extraheader breaks even a public-repo `ls-remote`, and still wins when the exact `insteadOf` mechanism from this diff is active alongside it.

**Why 3 review rounds + a design council missed this:** every round's own testing confirmed the superproject's *local* config does NOT reach the *submodule's own separate* git directory during `git submodule update --init --recursive` (still true, unaffected by this fix) — but nobody tested the standalone `ls-remote` precheck specifically, which runs in the superproject's own context and does inherit it. A real, previously-unverified gap between "what was tested" and "what actually runs first."

**Fix:** `persist-credentials: false` on the `Checkout` step. Confirmed safe — a full grep of this file shows nothing later pushes/fetches/pulls against `thoth` itself (only local `git diff`/`git log`), so persisting the default token was never needed. This *removes* a credential-persistence surface rather than adding one.

**Ceremony note:** found and fixed live, mid-debugging with the human, after `cifix`'s own 3 review rounds + council had already shipped. Human explicitly chose to commit-and-test-via-a-real-CI-run over a fresh red-team pass, given the fix is small, empirically reproduced, and permission-reducing — the real CI run this triggers is itself the verification.
