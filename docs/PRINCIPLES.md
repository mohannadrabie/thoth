# Working Charter — how this team works (anti-kafka rules)
The point of the process is confidence, not ceremony. These rules bind agents AND humans.

1. **Ceremony scales with risk.** Trivial change (docs, tags, comments): tests + self-review, ship. Standard change: ONE domain reviewer (the right one) + implementer. Critical change (guarded paths, prod-facing, security-relevant): red team + the relevant reviewer. Every non-trivial review also seats `cross-domain-reviewer` — the standing cross-domain pass (rule 9) — but it doesn't count against the cap below: it isn't a domain pick, it's the seam-check the Manager used to reconstruct ad hoc, now done by a receipted specialist. Never more than two *domain* reviewers unless the manager orders it, in writing, with a reason. **The tier table itself is the project's to extend.** `CLAUDE.md`'s Risk Tier Definitions are a default, not a fixture: a project may add tiers, rename them, or name classes of change that always land in one ("anything under `payments/` is CRITICAL"). State such a rule in an **ADR**, and by rule 9 it outranks the table in `CLAUDE.md` and binds the Manager's ratification. A project rule may **raise** the ceremony a class of change gets; it may never lower it below what that change's own blast radius warrants, and it can never drop a security, data-integrity, legal or safety change out of review.
2. **Every block names its unlock.** A gate that says "no" without saying "here is exactly how to proceed" is a defect — file it like one.
3. **Approvals expire; work doesn't wait.** Review reports are keys with dates. Deadlocked reviewers escalate to /resolve THE SAME DAY — decisions in hours, not standups.
4. **SURVIVES is a celebrated verdict.** Reviewers are not paid in findings. A clean pass, verified, is the goal — manufactured findings destroy auditor credibility scores.
5. **Findings are fixes, not blame.** Every finding is phrased as the minimal change that resolves it. No "who did this"; git remembers so people don't have to.
6. **Auditors get audited — and audits are discipline, not compliance.** /audit samples past reports monthly: evidence quality, false positives, softened findings, missed blockers. Reviewer credibility is a tracked score. The manager's decisions are in the sample too. There is no external body being satisfied here — the only question an audit answers is whether the work actually happened. An audit that rubber-stamps a claim it never checked protects nobody; it is worse than not auditing at all, because it hides the gap instead of showing it.
7. **The manager decides, the log remembers, the human overrides.** Manager decisions are logged with rationale + dissent recorded + a review-back date. Nothing is quietly final.
8. **One next step.** Any agent ending a turn must state the single most important next action. Nobody should ever wonder "what now?"
9. **ADRs are the architecture source of truth, and they outrank conventions.** Accepted ADRs — their `Rules for agents` (testable MUST/SHOULD) — are hard constraints ranked ABOVE CLAUDE.md's conventions. Convention vs ADR → the ADR wins; ADR vs ADR → the more specific wins. A rule you cannot satisfy is never silently violated: say so and propose an ADR change (`/…:adr-amend`). Never edit an accepted ADR's decision — supersede it with a new ADR and mark the old one `superseded`. When ADRs are adopted or amended, existing code is realigned through a **conformance triage**, not silent drift. Architecture decisions live only in ADRs — `docs/decisions.md` is the general Decision Log, not an ADR store. **Each domain reviewer reads only its own domain's slice of the ADR catalog** (filter `adrCatalog.adrs` by `applicableTo`) — a data-reviewer reads the data ADRs, not the network ones. **`cross-domain-reviewer` owns cross-domain collision detection and inter-lane gaps, as a real reviewer with its own dated report and receipt, not an ad hoc Manager read**: it runs on **every review path above TRIVIAL** — including the inline single-domain-reviewer path — reads the compressed catalog **once, whole and unfiltered** (no `applicableTo` slice), and checks the **diff — the changed files — against every applicable ADR outside the lane(s) the domain reviewer(s) covered**, plus hunts non-ADR functional/architectural gaps at the seams between the domains the diff touches. It checks the code, not the other reviewers' findings: a violation in a non-owning lane produces no finding there, so a findings-only check would miss it. This is the single-read design — `1 × whole catalog + N × slice` — deliberately chosen over `N × whole catalog`, because the per-review cost of every reviewer reading everything grows with the ADR corpus while the one compressed read does not. `cross-domain-reviewer` doesn't count against rule 1's two-domain-reviewer cap — it's the standing seam-check, not a domain pick. `/verify` re-runs a whole-catalog-vs-diff ADR pass as the pre-merge backstop — so reviewer-slicing never lets an out-of-lane ADR violation reach merge even if a run somehow skipped it.
10. **Evidence, not claims.** A review, a check, or a "done" is real only when its artifact is committed. Reviewers save their report **verbatim** to `docs/reviews/<scope>-<type>-<YYYY-MM-DD>.md` with the **raw command/test output** (passed/failed/**skipped** counts). A review that lives only in a chat transcript is a claim, not evidence, and opens no gate. "Skipped" is never "passed." Every report-producing agent also ends its turn with a compact `RECEIPT:` block — this is how it hands its verdict to the Manager cheaply, and it is a pointer to the evidence, never a substitute for it. Reviewers (and red-team/design-challenger) list **every** finding, one terse line each — `[ISSUE]`/`[SUSPICION]`/`[CLEAN]` status, a `[HIGH|MED|LOW]` severity on each issue/suspicion, and a `counts` line that is a checksum on the list (not a top-N — nothing is hidden by length, so there is no `counts>N` trigger). Build and debug receipts carry deterministic counts instead (criteria mapped, checks passed/failed/skipped) since there's nothing to tag. The Manager reopens the actual persisted report whenever `docs/receipt-check.mjs` flags it, and whenever its own judgement does: a terse line that reads worse than its severity tag, a claimed ADR violation, zero findings on a non-trivial diff, or a `[HIGH]` whose stated exposure looks wrong. The script owns the mechanical triggers (both checksums, verdict enum, contradicted verdict, `[HIGH]`/`[SUSPICION]`, unrun or failing checks under a clean verdict, an untagged finding or a `[HIGH]` tagged `derived`, missing `REVIEW_LOG` row, missing bug Issue, stale `HEAD:`, `humanRulingRequired`) so they are counted rather than recalled; it is advisory and never a gate — and reopens **every** report regardless on a CRITICAL-tier run. The cheap path only ever greenlights (trust-and-relay); a blocker, rework, or re-tier is declared only after a full read. Audit depth scales with blast radius, same as reviewer selection does.

    **`maat.json → reportStyle` trades prose for speed; it never trades away evidence.** Default `"full"`. Set `"lean"` to cut what makes a report long to read without cutting what makes it real: the `RECEIPT:` block (verdict, complete finding list, severities, evidence tags, the `counts` checksum, raw checks) is **always full-fidelity, in both modes** — nothing here ever shrinks it, because that block is what a gate reads. What `lean` shrinks is the surrounding prose every report-writing agent produces on top of the receipt: cap each finding's write-up in the body to evidence-citation-plus-fix (one to three lines, no restated background or narrative build-up), drop a written-out "context" preamble in favor of the scorecard, and keep the one-praised-decision line to a single sentence instead of a paragraph. This is a token/generation-speed lever, not a rigor lever — every check still runs, every finding still gets its full evidence tier and severity, round-counting and council triggers (rule 16) are untouched, and the pre-merge full-read gate (rule 11's neighbor, `ship.md` stage 5.5) still reads every report in full regardless of which mode wrote it. Toggle it any time by editing `maat.json` directly — no re-run of `/maat:init` needed — and toggle it back the same way if a report's compressed prose ever leaves a reviewer's own reasoning unclear; the receipt is never what suffers either way.
11. **Reports are immutable; verification is appended.** A persisted report is not edited after the fact — a finding that is later verified, disputed, or overtaken gets an **addendum** (or a follow-up dated report); the original evidence stays verbatim. High-severity findings are adversarially verified *before* they gate.
12. **Not in scope → backlog, never code.** Anything worth doing but outside the approved change goes to `docs/backlog.md` (with its origin, and a date if time-bound) — never into the diff as gold-plating. The backlog is where good ideas wait; the diff is only the approved change.
13. **Never skip a gate silently.** If a required gate (review, ADR check, DoD item, human approval) was skipped or could not run, STOP and say so plainly. A silently-skipped gate is the worst failure mode — worse than a failed one, because it hides.
14. **One state, read first.** Every session hydrates the same context, in order — `docs/STATE.md` (where things stand) → `CLAUDE.md` (hard rules) → this charter → `docs/decisions.md` (the **active** set only — resolved rows past their review-back date live in `docs/decisions-archive.md`, read on demand, so this hydration stays bounded as the project ages) → the applicable ADRs — before acting. The manager keeps `docs/STATE.md` current at every close so the loop resumes across sessions.

15. **Novel shape gets an architecture pass before the design-challenger loop, not instead of it.** A CRITICAL-tier story introducing this system's first-ever instance of a pattern (first background job, first cross-request state machine, first new managed service, first multi-batch or resumable write path) routes to `architecture-reviewer` BEFORE, or in parallel with, the first `design-challenger` round. The design-challenger's mandate is adversarial verification of a design already chosen; it attacks edges, it never asks whether the design should exist. That question is `architecture-reviewer`'s. Skipping this for a novel-shape story is a gate miss of the same severity as skipping any other required review.

    **Repeat-root-cause earns the same early pass, not only a first-of-its-kind shape.** When two consecutive `design-challenger` NO-GOs on the same story/thread trace to the same root-cause CLASS (not the same finding restated — the same underlying gap recurring in a new form), `architecture-reviewer` is dispatched automatically before the next round, not after a 3rd/4th repeat. This does **not** change design-challenger's own grading — only when `architecture-reviewer` joins. Where this condition and rule 16's root-cause-class counter (below) are satisfied by the same pair of rounds, rule 16's hard-stop governs — it is the stronger action; this rule's early, non-blocking dispatch still stands on its own for any `design-challenger` round outside the pre-build design loop rule 16 covers. **Calibration watch, not a mechanism to build:** `architecture-reviewer`'s track record rests on sparing use for real judgment calls — raising its dispatch frequency risks diluting that. Sanity-check its hit rate periodically; this addition is not free.

    **Disambiguation: "root-cause CLASS" here means one specific thing, not the other "root cause" usages already in this repo.** In rules 15 and 16, "root-cause class" is a Manager-judgment comparison, read from two `design-challenger` reports' free-text findings, of a repeating underlying gap/pattern recurring across those consecutive graded verdicts — never a structured field either report emits (`design-challenger.md` carries no such field), never `debugger.md`'s per-bug root-cause-vs-symptom diagnosis, never the Path-Forward Brief's post-hoc one-sentence `### Root cause` in `manager.md`/`council.md`, and never `docs/backlog.md`'s bypass-taxonomy "class" terminology.

16. **Stalled loops convene a council once, then escalate to a human — regardless of which loop stalled.** A design loop stops and convenes the **design council** (`/maat:council` — design-challenger + architecture-reviewer + impact-analyst, conducted by the Manager) the moment any of: **(a)** a round's fix demonstrably reverses something an earlier round's SURVIVES/CLEAN already established; **(b)** 2 GRADED VERDICTS pass without a GO in the **pre-build** `design-challenger` loop, counted by verdict and never by document or filename identity (an in-place fix batch that draws a graded verdict is its own round); or **(c)** 3 CONSECUTIVE REWORK/BLOCKED-class verdicts land on the same review target (the same story/PR/artifact) in the **post-build** review loop (`/maat:review`, or `/maat:ship` stage 3) without an intervening clean or conditional-clean verdict — counted the same way, by verdict, reset to 0 the instant a clean/conditional-clean verdict lands (raised from 2 to 3 so one early miss on an otherwise-ordinary story doesn't trigger full council ceremony); or **(d)** 6 TOTAL REWORK/BLOCKED-class verdicts land on the same review target in the post-build review loop, counted cumulatively across that target's whole history and never reset by an intervening clean/conditional-clean verdict — this catches the shape (c) alone misses: a target that finds one new, distinct issue per round, clears it, and finds another, so it never strings together 3 consecutive misses but is still taking as long as one that did. (a) and (b) are the pre-build design-loop triggers; (c) and (d) are the two hard stops for the post-build review loop — a change cannot cycle through review indefinitely without ever reaching either a clean verdict or a human ruling. Whichever trigger fired is named verbatim in the Path-Forward Brief (`**Trigger:** rule 16(a|b|c|d)`). The council runs **once per artifact per architecture**. Its verdict is computed, not negotiated: **GO** requires no open calibrated blocking HIGH, an architect APPROVE on a candidate path, an impact-analyst verdict on that path that is not WIDENS, and the artifact's gating verification run or scheduled as build task #1. **On GO the loop continues autonomously and no human is woken.** On NO-GO, or on a second stall against the same shape, the loop **hard-stops**: `humanRulingRequired` is set, further rounds are refused, and the Manager posts the Path-Forward Brief for a human ruling. Stopping has a default: when the loop stops and no OPEN finding is a calibrated blocking HIGH, the recommendation carried to the human is **"build now: every open finding becomes a day-1 failing test, and build task #1 is the artifact's own gating verification."** Another design round is the explicit override, never the default.

    **A second, independent counter — same root-cause class, not just round count — also forces the stop.** If the SAME root-cause class recurs in 2 consecutive GRADED VERDICTS, regardless of what the round-counter's own count in (b) is, that ALSO mandates the stop above, on the same terms: `humanRulingRequired` is set, further rounds are refused, the Manager posts the Path-Forward Brief. This counter is about routing and escalation timing only — it does not alter design-challenger's dispatch conditions, grading criteria, or verdict thresholds in any way; design-challenger still grades exactly as this rule and `design-challenger.md` already specify. Strictly additive to (a)/(b) above: it can only shorten how long a repeat-class failure runs before a human/architecture-reviewer decision, never replace or weaken the existing round-counter.

17. **The design deliverable is executable, not narrative.** For any story above TRIVIAL the design artifacts are, in order: (a) acceptance criteria written as a list of NAMED test cases; (b) a runnable spike that measures every number the design leans on (latency, capacity, row counts, timeouts); (c) at most a one-page shape note covering topology, blast radius, and evolution path. Prose beyond that is backlog, not design. For CRITICAL or novel-shape stories, a **walking skeleton** — the thinnest end-to-end path touching every layer against a real datastore — is built before design round 2, and rounds 2+ attack the skeleton, not the document. A design document that outgrows its one page, or a loop that reaches round 3, is a signal to build the skeleton, never a signal to write more.

18. **Numbers are measured before they shape anything.** No design decision, capacity limit, timeout, batch size, or architecture may rest on an unsourced figure. The spike that measures it runs first. A reviewer finding whose blast radius depends on an assumed number caps at LOW with the sole recommendation "measure it." An estimate presented as "the real number" is a finding against the reviewer, surfaced at `/maat:audit`.

19. **Only executed evidence can block.** Every finding declares `demonstrated` (a command was run, its raw output is in the report), `code-traced` (`path:line` in shipped code), or `derived` (reasoned from a document) — **as a tag on the finding's own line in the RECEIPT**, not only in the aggregate tally, because an aggregate cannot say which finding was derived. The receipt's `evidence:` line is then a checksum over those tags and must total the findings. Only the first two can gate a change; `derived` caps at MED and becomes a named failing test or a residual-register line. A reviewer whose receipt says `checks=n/a` may not carry a blocking finding. Findings convert to failing tests, never to numbered condition lists: `open findings` and `failing tests` are the same number, and any gap is explained.

20. **Ceremony is tiered by the artifact's usage profile, not only by its code path.** Before the first review round, the Manager records the tier from blast radius × frequency × reversibility: (a) recurring money/state hot path, full CRITICAL treatment; (b) one-time or migration-window operation with an undo/archive/reconciliation path, design-challenger budget of 3 graded rounds, residuals ship with a reconciliation report rather than design-proof; (c) internal tooling and instruments, single reviewer, findings become tests. A deadline that expires the artifact's value (a vendor sunset, a compliance date) is recorded in the tier note and weighs toward shipping with residuals. The tier is a ratified line in `docs/decisions.md`; reviewers read it and calibrate, they do not re-litigate it.

21. **A finding's blast radius is stated, not assumed — and a narrow one doesn't get to call itself a blocker alone.** Every `[HIGH]` finding (and any `[MED]` a reviewer wants to escalate) states an estimated affected surface on the same line as its severity — `Exposure: ~<N>% of <users|requests|runs>, basis: <measured|counted-in-code|assumption>` (the quantification `red-team.md` already requires, now required of every reviewer). A `[HIGH]` outside the security / data-integrity / legal / safety categories, whose stated exposure is under 3% of users and whose basis is not bare `assumption`, does not by itself force a REWORK/BLOCKED-class verdict — it is capped at non-unilateral-blocking and routed to the **Manager's severity triage** (`manager.md` Role 2b) before the loop treats it as gating. The reviewer still files it, still tags it `[HIGH]`, still states its evidence — this rule changes who gets the final call on whether it blocks ship, not whether it gets reported. Security, data-integrity, legal, and safety findings are **exempt from this cap regardless of stated exposure** — a one-user IDOR or a single leaked credential is still a blocker; this rule exists to stop cosmetic/edge-case findings from stalling ship, not to shrink real risk. A reviewer that cannot state a basis for its exposure estimate says so plainly (`basis: assumption`) rather than inventing a number — an invented-precise figure is itself a finding against the reviewer at `/maat:audit`. **A `basis: assumption` (or contested) exposure claim is never resolved by bouncing it back to the same reviewer that made it** — the Manager escalates it to the `impact-analyst`'s lightweight exposure-verification mode (`impact-analyst.md`) for a real, mechanically-counted figure, and rules using that number. The Manager keeps the final blocking-or-not decision throughout — the impact-analyst verifies the fact the decision rests on, it does not make the call itself.
