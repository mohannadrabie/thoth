## Context / threat model
The seal protects the git/rg exec levers up to the session write boundary: a session cannot author a settings env block
or write the config/attribute/hook files git reads, so a malicious session cannot plant a program git later runs. git/rg
stay unresolved (POL-05 denies), gate unwired (K held; deny rules inert outside the central layer). The preflight
qa:git-rg-lever-preflight is the designated machine-checkable re-add precondition (criterion 10,
S409-precondition-preflight-clean) and feeds the story G runbook: any finding blocks K and the re-add story.

## Findings, ranked by blast radius

### 1. BREAKS -- [HIGH][demonstrated + code-traced] Submodule git dir (.git/modules/adr) is neither sealed nor scanned
Exposure: ~100% of repos with a submodule (the adr/ submodule exists and is updated routinely via
git submodule update --init adr), basis: counted in code. Gate unwired, K held -> 0% of production runtime affected
today; the live exposure is on the re-add gate (the preflight) and on the deliverable sealed claim.

The protected list (src/qa/protected-path-list.ts:232-242) lists literal .git/config and .git/hooks/ but no
.git/modules/*/config or .git/modules/*/hooks/. The preflight (src/qa/git-rg-lever-preflight.ts:286-316, runPreflight)
scans only commonDir/config, gitDir/config.worktree, commonDir/hooks, commonDir/info/attributes of the repo root -- it
never enumerates .git/modules/. A submodule own config and hooks/ are live exec levers (core.fsmonitor, core.hooksPath,
core.sshCommand, hook files) that run when git operates on the submodule.

Demonstrated -- fixture repo with [core] fsmonitor = C:/evil.exe in .git/modules/adr/config and a post-checkout hook in
.git/modules/adr/hooks/, run through runPreflight:

    findings_count_total: 0
    counted(unacknowledged): 0
    []

protectedPaths(root).all module paths: []. The preflight reports CLEAN on a repo carrying a submodule exec lever;
S409-precondition-preflight-clean (the re-add gate) would pass green. Silent false-clean on the gate.

Trigger: a session writes .git/modules/adr/config (a file write, not a git command -- exactly the write class the seal
exists to stop for .git/config); later a human or CI runs git submodule update / any git op on adr/ and the planted
program runs. Already filed as Issue #440 (by app-security-reviewer); this run adds the demonstrated reproduction.

Proof-test before merge: S409-protected-list-covers-submodule-git-dir (asserts .git/modules/*/config and
.git/modules/*/hooks/ are in protectedPaths().all, or an explicit Issue-tracked scope exclusion) and
S409-preflight-detects-submodule-levers (the fixture above must return at least 2 findings).

### 2. BREAKS -- [MED][demonstrated + code-traced] Preflight executingKey misses several executing config keys
Exposure: pre-planted config (R3) only; these keys live in the write-sealed .git/config / ~/.gitconfig, so the write
boundary holds against a session -- the gap is detection of config that existed before activation. Basis: counted in code.

executingKey (git-rg-lever-preflight.ts:82-118) classifies as non-executing several keys that run a program.
Demonstrated -- all five return executing=false:

    core.alternaterefscommand | executing=false
    submodule.x.update         | executing=false   (update = !cmd)
    gpg.ssh.defaultkeycommand  | executing=false
    tar.tgz.command            | executing=false
    browser.x.cmd              | executing=false

Preflight reports clean on a pre-planted repo carrying these. Already filed as Issue #441; this run adds the repro.
Proof-test: S409-preflight-detects-exec-config-keys over the five above.

### 3. UNPROVEN -- [LOW][code-traced] System gitconfig detection hardcodes the Git-for-Windows install path
DEFAULT_SYSTEM_CONFIGS (git-rg-lever-preflight.ts:63) = /etc/gitconfig, C:/Program Files/Git/etc/gitconfig,
C:/Program Files/Git/mingw64/etc/gitconfig. A git installed by scoop/winget/choco to another prefix has its system
gitconfig missed -> preflight false-clean on system-scope pre-planted config. Not session-writable (R2, disclosed), so
the write seal is unaffected; this is a detection completeness gap, and avoiding git config --show-origin is a deliberate
no-spawn tradeoff. Caps at LOW; recommendation: measure where git real system config lives on target machines. No block.

## Attacks that SURVIVE (honestly assessed)
- Nested .gitattributes (main repo): SURVIVES -- an attribute can only select a driver that config defines, and main
  .git/config / ~/.gitconfig are sealed. (The submodule variant is part of finding 1.)
- GIT_DIR, GIT_CONFIG_*, XDG_CONFIG_HOME, RIPGREP_CONFIG_PATH env alternates: SURVIVES -- all are lever keys (GIT_/RIPGREP_
  prefix or named), caught by scanSettingsEnv, and a session cannot author the settings env block.
- .git/config.worktree + extensions.worktreeConfig: SURVIVES -- config.worktree is inert unless the extension is enabled
  in sealed .git/config; confirmed OFF in this repo (git config --get extensions.worktreeConfig -> exit 1). Preflight
  scans it anyway.
- includeIf / include.path targets: SURVIVES -- includes live in sealed config; the preflight follows them read-only,
  depth-capped (5) and cycle-guarded (seen).
- Lever-key env rule + snapshot instrument (attack b): SURVIVES -- default-deny by GIT_/RIPGREP_ prefix is robust by
  construction (no inert allowlist to rot); the 153-token vendored snapshot + drift test make the coverage test run where
  git is absent. The env-key rule is sound; the config-key detector is finding 2, a different surface.
- Preflight read-only / cannot be made to exec (attack c): SURVIVES -- S409-mutant-preflight-spawns-git (AST scan for
  child_process + writes) passes; reads files directly. Residual: a planted FIFO/huge include could stall it, read-only.
- Deny rules / K Edit entries cover case, separators, Windows forms (attack d): SURVIVES -- canonicalizePathTarget folds
  backslash/case/trailing dot+space; the hook cross-product test (redirect/tee/cp/mv/sed-i) passes for every new path.
- .githooks acknowledgement (attack e): SURVIVES -- KNOWN_PROJECT_CONFIG acknowledges core.hookspath=.githooks only in
  the repo own config (not worktree/user/system), on exact key AND value; .githooks/ is itself protected, so the
  acknowledgement opens no write path. Any other value, or the same key elsewhere, stays a FINDING.

## Scariest unproven assumption + go/no-go
Scariest: the preflight -- the designated re-add gate -- reports CLEAN on a repo carrying a submodule exec lever, so the
sealed-up-to-the-write-boundary claim and the machine-checkable re-add precondition both have a silent blind spot the
adr/ submodule makes real.

Verdict: no-go. Single next action: extend the protected list and the preflight scan to .git/modules/*/config and
.git/modules/*/hooks/ (finding 1, Issue #440), with a failing-first test; then re-run the seal suite.
