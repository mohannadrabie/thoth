## Verdict: APPROVE (the HIGH is closed and demonstrably so; two LOW hardening items remain, neither gates)

The printed unlock command can no longer carry a contributor-chosen character: a path outside `[A-Za-z0-9._/-]` gets a line that is not a command and shows the path percent-encoded. I attacked it with a broader hostile set than the implementer's, through the real CLI, pasting every printed line into sh, PowerShell and cmd in seven invocation modes: zero payloads ran from any line the tool tells a maintainer to use. The two new named tests were red at the test-first commit and are green now, and they kill 36 of 36 mutants I applied. Two LOW items are left: the how-to line gives no quoting advice, and the (unchanged, pre-existing) match lines still print the path as git spells it.

## Findings, ranked by exploitability x impact

### 1. [LOW][demonstrated] The how-to line sends the maintainer to the raw path but gives no quoting advice
- **Evidence.** `src/secret-scan/history-scan.ts:234-239` prints "quote the path yourself for your shell" and "the path spelled exactly as in the match line". The match line (`src/secret-scan/history-scan.ts:273`) holds the raw hostile spelling. The old danger returns only by a human step: hand-quoting with double quotes, the shape the tool printed before this round.
- **Attack sketch.** A contributor names a file with a command substitution and a secret-shaped literal; the maintainer follows the how-to, wraps the path from the match line in double quotes, and runs it.
- **Demonstrated (scratch, the tool's text followed literally).** Hand-quoted with double quotes, a payload ran in bash for 2 of 3 names and in PowerShell for 1 of 3 (the semicolon name is inert inside double quotes, as expected). Hand-quoted with single quotes: 0 of 3 in both shells. Following the how-to with single quotes and the path spelled as in the match line resolved and exited 0 for 4 of 4 spellings, including a C-quoted non-ASCII path and a path with an embedded double quote, so the how-to is accurate and the symptom of issue 238 is covered.
- **Exposure:** paths that need quoting are 1 of 370 tracked paths today (a space, benign), basis: measured (`git ls-files` count); it needs an attacker-named path AND a maintainer who double-quotes by hand. Not a blocker: the tool warns, hands over no loaded command, and the safe form is one sentence.
- **Minimal fix.** One sentence in that line: use single quotes in sh and PowerShell, never double quotes, and never paste a match line. A wording assertion is not worth a test; it resolves as a residual line or a backlog item.

### 2. [LOW][demonstrated] Pre-existing: the match lines print the path as git spells it, including raw C1, bidi and zero-width characters when `core.quotePath` is false
- **Evidence.** `src/secret-scan/history-scan.ts:257` and `:273` are unchanged by this round (absent from `git diff 5156eff HEAD`). Under git's default `core.quotePath=true`, control and non-ASCII characters are octal-escaped (10 of 10 hostile control and Unicode names came out escaped, in quotes). With `core.quotePath=false` (a common developer setting) 4 of 10 lines carried raw C1, bidi-override, bidi-isolate or zero-width characters into the log. Pasting these lines into a shell is not something the tool asks for, but it ran a payload: bash 16 of 156 line-runs, PowerShell 4 to 5, cmd 12 (names with an ampersand, a substitution or backticks).
- **Not a regression, not a workflow-command vector.** 0 lines start with a double colon, every detail line starts with two spaces and a dash, and every new line is ASCII-only (clean item 6).
- **Exposure:** as finding 1, basis: measured. **Fix:** display the path percent-encoded in the match lines too and keep the raw spelling only where the `hash` lookup needs it. Out of scope for this story (backlog): the lookup key is the raw spelling, and changing it is a design step.

[CLEAN][demonstrated] **Percent-encoding is injective and inert.** The shipped `percentEncode` source, extracted from the file and run: every one of 1,112,064 non-surrogate code points round-trips through a decoder with 0 failures and 0 charset or format violations (output is only `[A-Za-z0-9._/%-]`, each percent followed by exactly two upper-case hex digits). 200,000 random strings over a hostile alphabet gave 0 collisions and 0 round-trip failures. A literal percent is itself encoded (as a percent followed by 25), so a name that looks encoded stays distinct; through the CLI, 53 of 53 decoded paths equal git's spelling and the distinct count equals the row count in 7 of 7 batches.
