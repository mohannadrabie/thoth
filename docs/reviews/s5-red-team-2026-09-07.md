## 2. Findings, ranked by blast radius (exposure × irreversibility × silence)

### F1 — `[ISSUE][HIGH][demonstrated]` The diff silently disables 100% of S5's only live-wired enforcement

**Attack.** S5 ships two live hook entries and one deferred one. `PreToolUse` is deliberately not wired (verified, F14). That leaves the SUR-03 halt — SessionStart writes a halt-state file, UserPromptSubmit blocks on it — as **the entire live enforcement surface this story delivers**. `KNOWN_CONNECTORS` (7 entries) plus `centralLayer` (6 entries) are exactly, name-for-name, the set that was causing that halt to fire. Adding them does not narrow the gate; it turns it off.

**Scenario.** S5 merges. `docs/STATE.md` and `.claude/settings.json`'s header describe a live-capable halt mechanism wired at two events. A reader — a future reviewer, an auditor, the human at merge — reasonably concludes SUR-03 is enforced in this repo today. It is not. Every session start is a no-op, every prompt passes, no file is written, nothing is logged. A genuinely new, genuinely unclassified MCP server added tomorrow *would* still halt — the one thing keeping this from being a total bypass — but the mechanism's current live verdict on this machine is "nothing to see."

**Demonstration (pre/post, same real config, same machine):**

```

YES:

      "set": true,

The allowlists were authored by copying that `detail` string. `.thoth/halt-state/2ae1183c-….json` (written 2026-09-07 23:55 UTC, pre-diff) holds the identical two lines.

**Exposure: ~100% of sessions in this repo on this machine, basis: measured** (pre/post hook execution against the real `~/.claude.json` + `.claude/settings.json`).
**Silence:** total — exit 0, no file, no stderr, no log, no failing test (F10).
**Irreversibility:** the lines are trivially removable; the durable harm is the belief that a control is on.

**Current defense, honestly assessed.** Two in-code comments disclosing the stopgap, and a claim that "this operator explicitly reviewed and accepted" it. **I want to be fair about the motive.** The operator did not do this to weaken the product. The gate had become unusable and named no way out (F5). Suppression was the only exit the gate offered. The finding is not "never allowlist" — it is "this allowlist is an unscoped, unexpiring, uninstrumented, self-approved disabling of the whole control, shipped as part of a story whose headline claim is that the control exists."

**Verdict: BREAKS.**

### F2 — `[ISSUE][MED][demonstrated]` `centralLayer`'s `remote-mutating` labels are cosmetic; "classify" means only "exempt from halt"

**Attack.** The brief asked whether classifying six MCP servers `remote-mutating` has any enforcement consequence. It does not.

**Code trace.** `src/policy/tools/classification.ts:67-80` — `evaluateToolInventory` builds `byName` and branches solely on `byName.get(name)` being truthy. The `class` value is copied into `classified[]` and never compared to anything. `hooks/sessionstart-tool-enum.mjs:229-232` destructures `inventoryResult` and reads only `.haltRequired` and `.unclassified`; `.classified` is discarded. A repo-wide grep for consumers of `evaluateToolInventory` returns the hook plus its own tests, nothing else.

**Demonstration.** I added `{ name: "attacker-mcp", class: "read-only" }` to `centralLayer` — the *most* permissive bucket, on a name whose comment neighbours all say "mutates real infrastructure":

```
$ npm test
tests 513  pass 513  fail 0  skipped 0
$ npm run lint                    # clean
$ npm run qa:gate-command-path    # PASS: 2 command-type hook entries checked
```

`read-only` and `remote-mutating` are behaviourally identical. The per-entry risk rationale in the comments ("can plan/apply real infrastructure changes") documents a judgment the code never acts on.

**Current defense.** `src/policy/tools/builtin-tool-inventory.ts:22-25` already discloses this honestly ("the specific bucket ... does not itself gate anything yet, since no real central policy consumes it before S6"). That disclosure is why this is MED, not HIGH. What the diff adds is the *trap*: it applies the presence-only mechanism to the highest-risk names in the inventory (AWS API execution, Terraform apply, browser drive), inside the enforcement hook, with prose that reads like risk labelling. The next maintainer who adds an entry will believe they are labelling risk; they will be silencing a gate.

Adjacent, not duplicate: Issue #88 covers MCP-*provided tools* being unenumerated. This is about the `class` field having no consumer.

**Exposure: ~100% of `centralLayer` entries (6 of 6) carry a label with no effect, basis: counted-in-code** (zero consumers of `.class` outside tests).

**Verdict: BREAKS** (as an enforcement claim; SUR-03's own text is "the classification shall drive enforcement").

**Named proof-test:** `src/policy/tools/classification.test.ts` -> `"S5-F2: a tool's resolved class changes at least one downstream decision"` — currently unwriteable, which *is* the finding. Interim: add an explicit `// NOTE: presence-only; class is inert until S6` at the `centralLayer` site, and file the real test against S6.

### F3 — `[ISSUE][MED][code-traced]` A security allowlist keyed to an unverified third-party self-reported string — direct ADR-0021 INT-07 hit

**Attack.** `hooks/sessionstart-tool-enum.mjs:236` filters connector names through `KNOWN_CONNECTORS.has(name)` (negated). The only test applied to a connector before waiving the halt is **exact string equality**. `src/policy/tools/mcp-enumeration.ts:89-99` reads `claudeAiMcpEverConnected`'s raw string values and nothing else — by deliberate design (OPS-02 no-secrets purity) — so no connector ID, account binding, URL, scope list, or signature is available at this layer even in principle.

**ADR.** SE ADR-0021, accepted: *"No control named in thoth's posture output may rest on an unverified third party's claim about its own behavior; where thoth can verify a third party's gate directly, it MUST do so and record its own independent verdict (INT-07)."* Waiving a halt on a name the third party supplies about itself is exactly the shape that rule prohibits. There is no compensating verification anywhere on this path.

**Current defense.** The comment argues a connector "has no tool-schema to classify against" — true, and a fair reason the *halt* is coarse. It is not a reason the *exemption* can be coarse. The header even says the exemption "does not apply to any connector added to the account after this list was written" — but the code cannot tell "added after" from "named the same"; it only compares strings.

Secondary, derived from the key name only and not counted as its own finding: `claudeAiMcpEverConnected` is by its name a *historical* set, so the halt detects past connections rather than gating a new one before first use.

**Exposure: unquantified — see F4.** The absence of verification is code-traced fact; whether it is attacker-reachable is not established, and I am not inflating it.

**Verdict: BREAKS** (ADR rule unmet).

**Named proof-test:** `hooks/sessionstart-tool-enum.test.ts` -> `"S5-F3: a connector identity is matched on more than its display name"` — fails until the exemption carries a second, non-self-reported factor, or is removed in favour of F1's dated fixture.

### F5 — `[ISSUE][MED][demonstrated]` The new block message names the problem but not the unlock, and a halt reason is permanently sticky

**Attack.** PRINCIPLES rule 2: *"Every block names its unlock. A gate that says no without saying here is exactly how to proceed is a defect — file it like one."* The entire point of this diff was operator visibility. The message it produces:

```
thoth halt: session redteam-sticky-1 blocked -- SUR-03-unclassified-tool: unclassified: some-tool-since-removed
```

No remediation. The malformed branch *does* name its unlock ("until it is fixed or removed", line 164); the active-reason branch does not.

**Worse — nothing ever clears a reason.** `writeHaltReason` only ever sets. Demonstrated: with a stale `set:true` file present and every tool now classified, re-running SessionStart for the **same session id** leaves the file untouched, and the relay keeps blocking:

```
=== 1. SessionStart re-runs for the SAME session id, everything now classified ===
SessionStart EXIT=0
--- halt file after re-run: ---
{"sessionId":"redteam-sticky-1","reasons":{"SUR-03-unclassified-tool":{"set":true,...}}}
=== 2. relay for that session ===
RELAY EXIT=2
```

Session ids survive `--resume`. A session halted once is bricked for its whole lifetime with no stated escape and no mechanism-supplied one.

**Causal note.** This is the defect that produced F1. Faced with a gate that blocked every prompt and offered no exit, editing the source was the only path the mechanism left open. Fixing F5 is the durable fix for F1 motive.

**Exposure: ~100% of halted sessions, basis: counted-in-code** (one message-construction site, `blockWithMessage` line 109; no clearing code path exists anywhere under `hooks/`).

**Verdict: BREAKS.**

**Named proof-tests:** `hooks/userpromptsubmit-halt-relay.test.ts` -> `"S5-F5: every block message names a concrete unlock"` (assert the emitted `systemMessage` contains the halt-state path and the command that clears it) and `"S5-F5b: a halt reason set for a session is clearable"`.

### F6 — `[ISSUE][MED][demonstrated]` "Wrong-shaped fails closed" is false for four shapes — the relay fails OPEN on a valid-object-but-corrupt-`reasons` file

**Attack.** `hooks/userpromptsubmit-halt-relay.mjs:150-155` validates only the **top level** (not-an-object, null, or Array), while its own comment claims *"anything else means something wrote content this schema was never meant to hold."* `anyReasonSet` then returns `false` for any `reasons` that is not an object of `{set: true}` entries — and `false` means allow.

**Demonstration** (each shape planted as a real halt-state file, real relay invocation):

```
shape                                      exit  verdict
truncated JSON (torn mid-write)            2    BLOCKED (fail-closed)
empty file (post-truncate, pre-write)      2    BLOCKED (fail-closed)
bare null                                  2    BLOCKED (fail-closed)
array                                      2    BLOCKED (fail-closed)
bare string                                2    BLOCKED (fail-closed)
object, NO reasons key                     0    *** ALLOWED (fail-OPEN) ***
object, reasons is a STRING                0    *** ALLOWED (fail-OPEN) ***
object, reasons is an ARRAY of set:true    2    BLOCKED (fail-closed)
reason entry set is STRING "true"          0    *** ALLOWED (fail-OPEN) ***
reason entry set:1                         0    *** ALLOWED (fail-OPEN) ***
legit active halt (control)                2    BLOCKED (fail-closed)
legit cleared halt (control)               0    ALLOWED (correct)
```

Note the incoherence: `reasons` as an **array** blocks (an accident of `Object.values`), `reasons` as a **string** allows. The fail-closed property is not a property; it is a side effect of four unrelated type checks.

**Realistic triggers.** (1) An operator "fixing" the file exactly as F5 malformed-branch message instructs — deleting the `reasons` key yields a silent pass. (2) The **second writer the schema comment explicitly anticipates** ("a hypothetical future second writer own reason, e.g. S11b") encoding truth as a string or a number. (3) Any hand-edit.

**Exposure: 0% today, basis: counted-in-code** — exactly one writer exists (`writeHaltReason`, `sessionstart-tool-enum.mjs:128-139`) and it always emits boolean `set: true`. Non-zero the instant a second writer or a hand-edit lands, which the schema comment says is the plan.

**Verdict: BREAKS.**

**Named proof-test:** `hooks/userpromptsubmit-halt-relay.test.ts` -> `"S5-F6: a halt-state file whose reasons key is missing or non-conforming fails CLOSED"` — table-driven over the four fail-open rows above; validate the full shape, not just the top-level type.

### F7 — `[ISSUE][MED][demonstrated]` Criterion 17 fail-closed enumeration write is unreadable when stdin is the thing that failed

**Attack.** `sessionstart-tool-enum.mjs:223` initialises `sessionId = "unknown-session"` *before* reading stdin, inside the try. If stdin is unparseable, the catch writes the `SUR-03-enumeration-failed` reason to **`unknown-session.json`**. The relay, for the real session, resolves the real `session_id`, reads that id file, finds nothing, and exits 0.

**Demonstration:**

```
$ printf "not-json{{{" | node hooks/sessionstart-tool-enum.mjs

EXIT=0
--- unknown-session.json exists? ---

The file own comment (lines 218-222) asserts precisely the opposite: *"a malformed/empty stdin is exactly as much an internal exception during enumeration ... and both must still result in a best-effort halt-state write, never a silent no-halt."* The write happens. The halt does not. The fail-closed guarantee is void in exactly the one case that guarantee was written for.

**Pre-existing at HEAD** — this diff did not introduce it. In scope as a defect in a file under CRITICAL review, per the honest-disclosure norm this project already follows.

**Exposure:** 0% of well-formed sessions; ~100% of sessions whose SessionStart stdin fails to parse. **Basis: counted-in-code for the mechanism** (one code path, one fallback constant); **assumption for the frequency** — Claude Code documented contract says this should never occur, and I have no measurement saying it does. **Verdict: BREAKS.**

**Named proof-test:** `hooks/sessionstart-tool-enum.test.ts` -> `"S5-F7: an unparseable SessionStart stdin still produces a halt the relay for that session can read"` — currently unsatisfiable, which is the point. ### F9 — `[ISSUE][LOW][code-traced]` The empty catch blocks discriminate nothing and leave a non-EPIPE failure with zero trace

**Attack, as posed by the brief.** The four empty `catch { }` blocks at lines 123-125, 128-130, 201-203, 206-208 swallow *every* error, not just `EPIPE`. If the stdout write fails for `ENOSPC`, `EBADF`, or `EIO`, nothing is recorded anywhere — even though fd 2 is, in those scenarios, very likely still writable and would have carried a one-line note.

**Honest assessment of the design.** "Best-effort message, unconditional exit(2)" is the **right** design and I am not arguing against it — the security property is the exit code, and F12 shows it now holds under every condition I could construct. The gap is diagnostic only: an operator debugging "the hook blocked and said nothing" cannot distinguish a dead pipe from a full disk. The fix is small and does not touch the exit path.

**Also within this attack, and it survived:** I looked for a path where the catch could mask a bug that should have been loud. There is none reachable — `blockWithMessage` performs no logic after the writes except `process.exit(2)`, and the top-level handler is identical. Nothing decision-bearing sits inside a try.

**Exposure: ~100% of non-EPIPE write failures produce zero diagnostic trace, basis: counted-in-code** (four empty catch blocks, no error discrimination in any of them). Diagnostic-only impact.

**Verdict: BREAKS** (minor).

**Named proof-test:** `hooks/userpromptsubmit-halt-relay.test.ts` -> `"S5-F9: a stdout write failure is noted on stderr and still exits 2"`.

### F11 — `[SUSPICION][LOW][code-traced]` Writer/reader project-dir divergence
