## Seam findings

### 1. [ISSUE][MED] Hand-derived, non-instrument-backed completeness claim in the shipped close-out prose - violates CLAUDE.md's "No hand-derived completeness claims" hard rule, and QA-15's own checker doesn't catch it

**Evidence (code-traced + demonstrated):**
- docs/plans/qa14-marker-redesign-phase1-2026-09-11.md:56-59: "I measured, via a scratchpad probe
  (not committed - reproducible: walk every tracked .md/.ts/.mjs/.js/.json/.yml file ... classify each
  bare ... match) ... marked=530 unmarked=1399 (would become unclassified) total=1929". This is the single
  load-bearing design justification (section 5.1) for the biggest call in the whole redesign: whether a bare
  parenthesized #N counts as marked. The plan itself calls it "the one genuinely load-bearing derived
  consequence."
- CHANGELOG.md:19 repeats the identical unverifiable figure verbatim in the shipped, committed close-out
  entry: "section 5.1's own measurement, reproduced from a scratchpad probe (not committed): marked=530
  unmarked=1399 total=1929 - approx 73% of this repo's bare-#N occurrences carry no explicit marker".
- CLAUDE.md hard rule: "No hand-derived completeness claims. Any claim of completeness/exhaustive
  enumeration ... is generated by a running instrument ... never hand-typed or hand-derived in prose. If no
  such instrument exists, building one is part of the task." The proportionality exemption ("a short, flat
  set that's genuinely trivial to eyeball") does not apply - 1929 occurrences across the whole tracked tree
  is not eyeball-trivial.
- Demonstrated the automated backstop does not catch this shape: `node src/qa/completeness-claim-checker.ts`
  (QA-15, scans docs/STATE.md + CHANGELOG.md by DEFAULT_FILES) returned "PASS: 2 file(s) checked, all
  completeness claims verified." - despite CHANGELOG.md:19's claim being present in a scanned file. Root
  cause: BARE_CLAIM_PHRASES (src/qa/completeness-claim-checker.ts:66-72) only matches "all N"/"every
  N"/"N of N"/"full set of N"/"exhaustive...N" - a raw "X=N Y=N total=N" / "~NN%" count shape is outside its
  five-regex heuristic. This is the exact seam a domain reviewer attacking reference-resolver.ts's own
  logic, or QA-15's own logic in isolation, would not surface: the defect lives in the prose the build
  wrote about itself, checked by a different instrument than the one under primary review.

**Why this is contained, not a blocker on its own:** the redesign's other invariant ("nothing here can newly
promote a previously-resolved match into a blocking verdict") does not depend on the 73% figure being
correct - bare unmarked #N becomes unclassified (non-blocking) either way, whatever the real proportion
turns out to be. The wrong number could not flip a citation from safe to blocking. That containment is why
this is MED, not HIGH, under the evidence policy's blast-radius rule - but it is a real, named hard-rule
violation in a committed, CRITICAL-tier close-out artifact, not a stylistic nit.

**Exposure:** 1 load-bearing design claim in this story's own close-out prose (CHANGELOG.md:19, plan
section 5.1), basis: code-traced. Does not change any citation's pass/fail outcome (contained, see above).

**Minimal fix:** commit the scratchpad probe as a real script (e.g. scripts/qa14-marker-corpus-probe.mjs),
re-run it, and either (a) register it in KNOWN_INSTRUMENTS (completeness-claim-checker.ts:45-54) and cite
it with a `[[completeness: cmd="..." expect=1929]]` marker in the CHANGELOG/plan text, or (b) if a one-off
probe isn't worth registering as a standing instrument, rephrase the claim to state it as an illustrative,
non-exact sample rather than a precise count. Either resolves the hard-rule violation; (a) is more in the
spirit of "if no such instrument exists, building one is part of the task."
