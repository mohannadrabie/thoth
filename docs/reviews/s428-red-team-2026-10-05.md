### FINDINGS

#### F1 (MED, code-traced) — Windows trusts the whole Program Files tree by PATH alone, no writability check; a user-writable Program Files subdir on PATH is a wrong-ALLOW
- Attack: a third-party installer puts its bin dir under C:\Program Files\<App>\..., adds it to PATH, and grants Users:(M) on it (a well-known Windows ACL/privesc antipattern). A non-elevated session plants kubectl.exe (or an E0 read binary) there with the Write tool, then issues the bare call.
- Current defense, honestly assessed: isTrustedRealDir (bare-binary-trust.ts:223) returns true for ANYTHING under the Program Files trees purely by path match — no owner/mode/effective-access check. Contrast POSIX, which runs posixChainTrusted (uid==0 and no group/world write up to /). The planted file sits in a trusted dir: phase 1 never scans it (trusted dirs are not shadow-scanned), and phase 2 accepts it as the trusted hit whose realpath stays in the Program Files tree -> ALLOW.
- Why the plan residual (c) understates it: (c) says an elevated session can write Program Files. This path needs NO elevation — only a pre-existing user-writable subdir that is also on PATH. A real, common misconfiguration, not operator error.
- Exposure: ~0% of live calls (gate unwired, K held); once wired, bounded by a user-writable dir under Program Files that is also a PATH entry existing on the target machine. basis: assumption (caps at MED). Not present on this machine (Docker bin dir read-only non-elevated).
- Verdict: BREAKS (narrow trigger, fail-closed philosophy violated for Windows). Irreversible (arbitrary exec under an allow record), silent.
- Named proof-test before K: src/policy/gate/bare-binary-trust.test.ts::TRUST-18-windows-user-writable-trusted-subdir-demoted — fake ports where a Program Files subdir on PATH is reported user-writable; assert the planted name there is NOT accepted as a trusted hit (add a Windows effective-writability probe to the port, OR an explicit tested documented-residual widening decisions.md (c) from elevated to any user-writable dir under a trusted root on PATH). If accepted as residual, the test asserts the deny reason / decisions.md wording — not silence.

#### F3 (MED, code-traced) — any untrusted PATH dir that EXISTS but is unreadable (EACCES) turns an allowed call into a deny; on a CI runner this can flip AC-2 red
- Attack / trigger: check() scans every untrusted PATH dir with readdir; ENOENT/ENOTDIR -> skip, any other error (EACCES, EIO, ...) -> deny(unreadable-dir) (bare-binary-trust.ts:341). A GitHub ubuntu-latest runner carries many tool-cache/opt dirs on PATH; if a future image adds an existing-but-unreadable untrusted dir, AC-2 (kubectl get, real hook) flips to deny and the DoD tests-green-in-CI breaks.
- Current defense: fail-closed, correct for the live gate (an unreadable dir could hide a plant). Cost is CI brittleness and, once wired, over-denial of legitimate calls on hosts with an unreadable PATH dir.
- Exposure: ~0% today; once wired, bounded by a non-ENOENT-erroring untrusted PATH dir on the host. basis: assumption (caps at MED). Not observed here (TRUST-13 clean run allows).
- Verdict: BREAKS (CI/mergeability + future over-deny), fail-closed so not a security hole. Named proof-test: hooks/pretooluse-kernel-gate-path-trust.test.ts::TRUST-19-unreadable-untrusted-dir-reason-is-actionable — assert the deny reason names the dir and the fix; confirm the CI image PATH has no such dir (or document the dependency) before K. Settle the CI half with F2 ubuntu run.
