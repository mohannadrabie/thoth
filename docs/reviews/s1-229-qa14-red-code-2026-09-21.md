### Finding 1. [ISSUE][MED][demonstrated] CHANGELOG.md: the s1-237 entry lost its heading; its text is glued to the end of the new entry

- **Evidence.** On master the first Unreleased entry opens with a level-3 heading for the s1-237 fix, at line 7. On this branch the only heading above the s1-136 entry is the new s1-229 one (line 7). Commands: `git show master:CHANGELOG.md` and a grep for level-3 headings on both sides; printing line 21 of the branch file ends with the old heading tail. Introduced by commit dd11898.

- **Minimal fix.** Move the tail off line 21 back onto its own line as the level-3 heading for the s1-237 entry above the paragraph at line 23, restoring the master text of that heading verbatim; leave the rest of the s1-229 entry as is.
- **Executable form.** None beyond the heading census command above; a docs-structure defect has no unit test in this repository.

### Finding 2. [ISSUE][LOW][demonstrated] An added line that starts with a bare number is not checked when it directly follows an unchanged line ending in the word "issue"

- **Evidence.** `src/qa/reference-resolver.ts:144` matches the word form with a whitespace class between the word and the number, so it spans a newline. In a whole-file scan an old line ending in the word "issue" followed by an added line beginning with a hash and digits is one blocking citation. In added-text-only scope the old line is not in the scanned text, so the added line is a bare number with no marker: "unclassified", non-blocking. `src/qa/reference-scope.ts:307` also inserts a break between runs, including two added lines that are adjacent in the new file with a removed line between them.
- **Demonstrated end to end** in a scratch repository: a CHANGELOG whose last line ends with the word "issue" and a commit appending one line that begins with a nonexistent number. Diff mode: exit 0, 1 citation, 1 unclassified. The same head at the zero SHA (whole file): exit 1, 1 of 2 failed. This departs from ruling (d): nothing a diff adds is exempt.
- **Exposure:** small; basis: assumption (the shape needs a line ending in that exact word followed by a line starting with a bare number; I did not count it in the corpus). Capped at LOW by rules 18 and 21: measure it before it shapes anything.
- **Minimal fix.** Either record it in the residuals (one bullet in the CHANGELOG entry and the plan) or, if the Manager wants it closed, carry the previous unchanged line's last word into the scanned text for a run that starts right after it.
- **Executable form.** Named test to add: an added line starting with a bare number after an unchanged line ending in the word issue is checked. It fails today.

## 8. The Manager's decision: are the two size drivers justified?

I built each simpler alternative in the throwaway clone and ran the committed 38 tests against it. This is measured, but the alternatives were not run through lint, typecheck or the mutation list.

**Parser (about 75 lines: `ParseState`, `readHunk`, `recordAdded`, `recordRemoved`, count arithmetic).**

- The build report's stated reason, that a content line shaped like a file header must not start a new file, does not require hunk counts. Every content line inside a hunk starts with a space, a plus, a minus or a backslash, and a diff-header line for a new file cannot be content. So a two-state scan (in a hunk or not; header lines are read only when not in a hunk; the per-file header line resets) is equivalent for git output.
- Measured: with that scan swapped in (about 36 lines for the function, no helper types), 38 of 38 tests pass, including the header-spoof and the real-git parse tests. File length 357 to 318.
- **Ruling requested: over-built, not wrong.** Correct as shipped and safe; replace it if the human's simplicity preference is to be honored. There is no desync path with git-produced diffs, so the count logic buys nothing.

**Tokenizer (about 65 lines of `skip*`, `objectMembers`, `collectMirrorSpans`, plus the cut).**

- The build report's reason is real: parse-and-reserialize drops the earlier value of a duplicate key, so authored text could hide. The tokenizer keeps the original text and is correct on the real file (section 7).
- Simplest safe alternative, measured: parse; accept the file only if it equals the two-space `JSON.stringify` of its parse (after normalizing CRLF and a trailing newline); set each `adrCatalog` object on the root and along the `priorScope` chain to null; return the re-serialized text. Equality proves the parse lost nothing (no duplicate key, no escaped key, no stray text); anything else is returned whole, the same fail-closed direction. About 20 lines. With it swapped in, 38 of 38 tests pass and the real file gives 3 catalogs cut, structurally equal to the reference. File length 357 to 279.
- The real file is exactly that canonical form (checked: equal to the stringify output plus one newline). Cost of the alternative: it depends on the tool that writes the file keeping that format. If the format ever changes, QA-14 goes red loudly on the mirror text (fail-closed), which is a visible, fixable failure.
- **Ruling requested: justified as built, and more than the risk requires.** If the human prefers simplicity, take the alternative; if the writer's format cannot be relied on, keep the tokenizer and add the escape test from finding 3.

Other surface points: the public names (`buildScanTexts`, `stripAdrCatalog`, `isAppendOnlyRecord`, `parseUnifiedDiff`, the three constants) read clearly; the 37-line header comment states scope, reasons and the fail-closed list; helper functions stay under the ADR-0010 size guidance; the density matches `reference-resolver.ts`. ADR-0010 sets no numeric file-size limit for the 357-line total.
