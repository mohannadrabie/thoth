## Attacks, ranked by exposure x irreversibility x silence

### 1. K5 certifies a gate entry that cannot block. BREAKS. [HIGH][demonstrated] (Issue #458)

Assumption: "the gate entry's command, matcher and timeout equal the proposal" means "the gate runs and can block". It does not. The vendor hooks doc lists these command-hook handler fields: type, command, args, if, timeout, statusMessage, once, async, asyncRewake and shell. `checkK5` (src/qa/k5-pretooluse-entry-uses-launcher.ts:37-45) checks three of them and nothing at the settings top level. Vendor semantics for what it ignores:

- `async: true`: "runs in background without blocking". The gate's exit 2 or deny is ignored.
- `if: "<rule>"`: "The hook command only runs if the tool call matches the pattern." `"if": "Bash(__never__)"` means the gate never runs.
- `args`: `command` "is resolved as an executable and spawned directly" with no shell. The `sh "...launch-gate.sh" "...gate.mjs"` string then fails to spawn as one executable name, which is a non-blocking error.
- `shell: "powershell"`: runs the `sh ...` line under PowerShell.
- top-level `disableAllHooks: true` in project settings: "To temporarily disable all hooks without removing them".

E2 shows all five read K5=PASS. The merge generator IS strict about the gate entry: k-settings-merge.ts:64 compares the whole entry by JSON.stringify. But it silently carries a pre-existing `disableAllHooks` or `env` block through (A1, "existing keys preserved"), with no warning (E2, last line). No other readiness row looks at these keys: `grep -ln disableAllHooks src hooks docs/qa` returns only src/qa/k-runbook.test.ts.

Production trigger: the human sets the vendor's own documented switch, `"disableAllHooks": true`, in .claude/settings.json to get a working session during K (the runbook's own section 6 names it as an escape hatch). Later, a re-run of `node src/qa/k-settings-merge.ts --write` keeps the key, K5 and K3 print PASS, and `qa:k-readiness` shows the K5 row green. The gate is off and every certificate says it is on. A later hand edit or merge-conflict resolution that adds `async` or `if` has the same effect.

Current defense: the 8 K5 mutants (command and matcher only), and the merge's exact-entry check on re-merge. That check throws on an extra handler key, but not on a top-level key, and K5 does not share it. Honest assessment: the instrument meant to make "a check that passes on a bypassable file" impossible passes on 5 of 5 documented bypass forms.

Exposure: ~100% of settings files carrying any of the 5 tested neutering forms pass K5 (5/5), basis: measured (E2). Today's .claude/settings.json has 0 such keys, basis: measured. The defect is not irreversible on its own, but it is silent: nothing reports it. Rule 21 note: today's exposure depends on a human edit, so the Manager may route this HIGH through Role 2b triage. It is still a demonstrated false PASS in a certification instrument.

Required before merge (one failing test): `K5 mutant set: neutering handler keys and disableAllHooks fail`. It is data-driven over async, if, args, shell, asyncRewake, once, an unknown key and top-level disableAllHooks:true. Simplest fix: K5 asserts that the gate entry deep-equals the merge's own `entry` object (the merge already builds it) and that top-level `disableAllHooks` is absent or false. The merge refuses, or loudly reports, an input that carries `disableAllHooks: true`.

### 2. `--form=absolute` emits a form Claude Code cannot match on Windows. BREAKS. [MED][demonstrated] (Issue #460)

Assumption: `Edit(//C:/playground/...)` is "the `//`-prefixed absolute form". Vendor permissions doc: "On Windows, paths are normalized to POSIX form before matching. `C:\Users\alice` becomes `/c/Users/alice`, so use `//c/**/.env`." E3 shows the emitter keeps the drive colon and the upper-case letter (protected-path-list.ts worktreeEditLines: `resolve(root, t).split(sep).join("/")`, then one leading `/` is stripped). The unit test (protected-path-list.test.ts:46-50) builds its expected value with the same transform, so it cannot catch this.

Production trigger: stage 1 probe P-K4 (docs/plans/s308-K-stage1-probe-plan-2026-10-05.md:44) tests "linked-worktree targets in `--form=relative` and `--form=absolute`; the form that is refused becomes #442's answer (if neither, #442 stays disclosed)". If the absolute candidate is malformed, P-K4 can conclude "absolute does not work" or "#442 stays disclosed" when a correct `//c/playground/thoth/.git/**` would have worked. Paid probe spend then produces a wrong answer, and a working protection is never wired. All worktrees on this project's platform are affected.

Current defense: P-K4 (live) would show the miss, but not its cause. This is not a bypass at stage 0, since nothing is wired.

Exposure: 3/3 absolute lines emitted on this Windows worktree use the undocumented form, basis: measured (E3). Every Windows linked worktree is affected, basis: counted in code.

Required: `worktree-targets: absolute form uses the documented Windows POSIX drive form (//c/...)`, a win32-conditional expectation written from the doc rather than from the same transform. P-K4 must run with the corrected candidate.

### 3. The K1/K4 readiness rows ignore what the row decided. BREAKS. [MED][demonstrated] (Issue #461)

Assumption: "a decisions row whose decision text starts with K1 and whose Human ratified cell is Y" means "the human approved K". k-readiness.ts:171-173 accepts any K1-prefixed row with Y, whatever the row decided. E4: a ratified "**K1 declined:** ..." row reads PASS. k4Row (lines 182-184) matches the substring `THOTH-ADR-0003 accepted` anywhere in the row, so "waits until THOTH-ADR-0003 accepted by the human (not yet)" reads PASS. (Today's real K4 row is a genuine acceptance, so K4 is correct at HEAD.)

Production trigger: in this project the Manager, not the human, writes decisions rows, and records each human ruling with Human ratified = Y. A human declining or deferring K is a normal ruling ("not this week"), and its faithful record is a K1-prefixed row with Y. Months later, readiness prints K1 PASS. A second-order problem runs the other way: k1Row requires the cell to be exactly `Y`, while this file's own convention writes `Y (human, 2026-10-05: "...")` (5 such rows today), so a genuine approval in the house format false-FAILs. The two rows are also inconsistent with each other: k4 uses `/^Y\b/`.

Current defense: readiness reads the working-tree docs/decisions.md, not origin/master, and nothing else corroborates K1. The human's merge of the wiring is the real backstop.

Exposure: 100% of K1-prefixed ratified rows pass, whatever they decided, basis: counted in code (k-readiness.ts:171-173).

Required: `k-readiness: a K1 row that does not record approval does not pass`. Fix: require a fixed token (e.g. decision text starting `K1 approved`) plus `/^Y\b/` as in k4, and anchor the K4 match the same way.

### 4. K5 ignores every other PreToolUse group and every other hook source. UNPROVEN-pending-verification. [MED][demonstrated]

K5 keeps only the one group that names the gate (k5:32) and ignores the rest. E2: a second group `{"matcher":"*", ...}` running a different script passes K5 and every other readiness row. gate-command-path only needs the script to exist, and gate-manifest counts files, not groups. Vendor docs: "All matching hooks run in parallel". The hooks doc does not say what happens when parallel hooks return conflicting decisions or more than one `updatedInput` (searched; not found). The permissions doc does say a hook "allow" cannot override a deny rule, so an allow-only group cannot defeat K3's Edit denies. What stays unproven is whether a parallel group that returns `updatedInput` rewrites the call after the gate has judged the original.

Settle: a stage 1 live probe (human-authorised spend). Wire two PreToolUse groups, the second returning `updatedInput` that rewrites `ls` into a gated command, and observe what runs. A cheap fail-closed rule needs no probe: `K5: any PreToolUse group other than the gate entry fails unless allowlisted`. Owners: Manager (probe plan) and story-implementer (test).

### 5. Sessions started outside the repo root load no project hooks or denies. UNPROVEN. [MED][derived]

Vendor permissions doc: "Hooks and other `.claude/settings.json` keys load from the current working directory's `.claude/` folder with no parent-directory fallback." A session started in `src/`, or any other subdirectory, loads neither the gate nor the generated Edit denies. Runbook section 1 says "Every Bash, Monitor, PowerShell, RemoteTrigger and `mcp__` call goes through the gate" with no working-directory precondition, and no P-K probe covers this case: grepping the K wiring plan, the stage 1 probe plan and the runbook for subdirectory, primary working directory and cwd gives no hits. `/cd` is user-only ("Claude can't call it"), so a session cannot use it to unwire itself. The problem is a coverage claim that holds only for repo-root sessions.

Settle: a P-K probe ("start a session in `src/` of the wired clone and attempt a gated Bash call"), plus `runbook: states the repo-root working-directory precondition`.

### 6. The matcher is an unanchored regex, but K5 and matcher-drift treat it as exact tokens. BREAKS. [LOW][demonstrated]

The proposed matcher contains `.` and `*`, so Claude Code evaluates the whole string as an unanchored JS regex (hooks doc). E5: it also matches `BashOutput`. The settings comment says the gate refuses, fail-closed, every tool name other than Bash and `mcp__`, so a wired session loses BashOutput. That is an over-match and fails loudly; it is not a bypass. K5's drift check splits the matcher on `|` and never evaluates it as a regex, so it cannot see this.

Required: `K5: every vendored tool the matcher regex matches is an intended token` (RegExp.test over the inventory), or, after a probe, anchor the matcher (`^(Bash|Monitor|PowerShell|RemoteTrigger)$|^mcp__`).

### 7. Readiness ties rows to npm script names and working-tree files. BREAKS. [LOW][code-traced]

k-readiness.ts:136-146 reads package.json from the working tree and runs whatever `node src/qa/<file>.ts` the named script points to; line 169 reads the working-tree docs/decisions.md. If `qa:k5` is repointed to any green `src/qa/*.ts` (a rename or a copy-paste slip), the "K5 (real file)" row reads PASS. The header's "read-only by construction" holds only as far as each named script is itself read-only.

Required: `k-readiness: script rows bind to fixed file paths, not npm script names`. SCRIPT_ROWS carries the file path, and the package.json script is checked to equal it.

### 8. Mods can override deny rules and hook blocks, and readiness does not pin the Claude Code version. UNPROVEN. [LOW][derived]

Vendor docs: on a machine without managed settings or a Team/Enterprise sign-in, a mod handling `tool.check` "can approve a call that a deny rule refuses". It can also approve a call a PreToolUse hook blocked, unless that hook is in managed settings. Mods are on by default from v2.1.287; this machine runs 2.1.267. `~/.claude/plugins/` is already in the protected list, so a session cannot plant a mod through Edit. What remains is an upgrade combined with any installed mod. Settle: add a readiness row that records `claude --version` and the `/plugin` mod count, or a disclosed residual line. Measure first.

### 9. Env-block levers pass through the merge unflagged; the only guard is the k-blocker label staying open. UNPROVEN. [LOW][derived]

E2: an `env` block with `NODE_OPTIONS` passes through `mergeSettings` without a warning. `isLeverKey("NODE_OPTIONS")` and `isLeverKey("SystemRoot")` both return false, so git-rg-lever-preflight does not report either key. Today's defense is the `k-blocker` label on #406 and #397. Once those Issues close, nothing reports a lever env block at merge time, and this repo has already closed an Issue by commit keyword by accident. Settle: `k-merge: an env block in the input is reported on stderr`.

### 10. K3 shadowed by allow rules, a hook allow, local settings or bypass mode. SURVIVES. [derived]

Vendor docs: "Rules are evaluated in order: deny, then ask, then allow ... An allow rule can't carve an exception out of a deny rule"; "if user settings allow a permission and project settings deny it, the deny rule blocks it"; "PreToolUse hook decisions don't bypass permission rules." K3 reading PASS on the allow/bypass variant (E2) is therefore correct. Deny under bypassPermissions is already a P-K4 item. The K wiring plan's risk table discloses the lower-cased entries (`~/.claude/claude.md`) and sends them to P-K4.
