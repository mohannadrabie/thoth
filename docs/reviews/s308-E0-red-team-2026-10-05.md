## Attacks, ranked by exposure x irreversibility x silence

### 1. [ISSUE][MED][demonstrated] A double-slash operand reaches a network path, and the record names a different, local path
- **Scenario:** a prompt-injected file asks the agent to read a double-slash path with one of the table commands (cat, ls, grep -r, head).
  - Git Bash/MSYS treats a leading double slash as a UNC path, so the read opens a remote SMB (or WebDAV) connection.
  - The normalizer canonicalises the operand to a single-slash local absolute path.
- **Evidence:**
  - Pre-E0 (6f78aee): all five probed double-slash shapes DENY.
  - Post-E0 (77a5b82): all five ALLOW. Example record: verbs read, target `/evilhost/share/x` for an operand that began with two slashes.
  - cygpath maps the double-slash form to a UNC path, and the single-slash form to a directory under the Git install. The recorded target names a different object than the one opened.
  - An ls of a loopback admin-share path listed real Windows directory entries, so SMB resolution through this shell is real. The gate refuses the dollar sign that admin shares need, so this proves the shell semantics, not a gate bypass of that character.
  - Code: `src/policy/normalizer/readonly-catalog.ts` BARE_WORD admits the slash. `src/policy/normalizer/path-canonical.ts:18-20` drops empty segments, which collapses the double slash.
- **Current defense:** none in E0. Before E0, every one of these shapes was denied as unresolved.
- **Exposure:** ~0% of live runs today (gate unwired). Post-K: 0 of 28 corpus accept rows use a double-slash operand (basis: counted in code). The trigger is adversarial only.
- **Why MED, not HIGH:**
  - An ALLOW does not auto-approve.
  - Reads are free by design (ruling 2).
  - The credential-forwarding side of SMB auth is vendor-documented behavior, not demonstrated here.
- **Fix:** refuse an operand whose raw text begins with a double slash in isBarePath.
- **Named failing test:** `RO-unc-operand-unresolved` (the five shapes must not be clean reads, and must DENY through the hook).
- **Issue:** #436 (filed by app-security-reviewer). Corroborating comment added.

### 2. [SUSPICION][LOW][code-traced] Recursive reads record the root, so a future subtree-scoped read-deny cannot match them
- **Scenario:** a future read-deny on `secrets/` (#435) is defeated by a recursive grep of `.` or `ls -R secrets`, because the recorded target is `.` or `secrets`.
- **Code:** `src/policy/kernel/kernel.ts:136-137` matches a trailing-slash pattern by startsWith. The target `secrets` does not start with `secrets/`, and `.` matches nothing.
- **Exposure:** 0% today. The shipped defaults contain no read or list deny rule (counted: 64 rules, none with verb read or list), so there is no live bypass.
- **Named failing test:** `RO-recursive-root-vs-subtree-read-deny` (kernel layer). It must land with #435, the first read-deny.
- **Issue:** #437 (already filed). No new issue, because this is LOW.
