## 1. Test code fence

hooks/sessionstart-tool-enum.mjs:238-241:
```js
const fixturePathOverride = process.env.THOTH_S5_CENTRAL_CLASSIFICATION_FIXTURE_PATH;
const fixture = fixturePathOverride
  ? loadCentralClassificationFixture(fixturePathOverride)
  : loadCentralClassificationFixture();
```
end test

`REQUIREMENTS.md:70` (§0.4, "What 'centralized' means," property 2 — a **named, load-bearing requirement text**, not a convention): *"Session cannot write it — the policy source is not reachable with any credential the governed session holds. A change under review cannot alter the rules that judge it."*

**This is a VIOLATION of §0.4 property 2, independent of exploitability, and independent of activation state.** The requirement doesn't say "the policy source must not be *successfully* rewritten by an attacker this session" — it says the session must hold **no credential reaching it at all**. An ambient environment variable, honored unconditionally by the shipped production entry point with no test-only marker and no DI seam, *is* a credential-free-session-reachable route to the policy source by construction.

Removing the specific exploit (e.g., gating the var behind `NODE_ENV=test`) would still leave the general shape wrong if the gate itself is another ambient signal the session's own environment can set. The fix that actually satisfies section 0.4 property 2 is not "make the override harder to trigger" — it is "the production entry point must have no override at all; a test harness that needs to inject a different fixture does so via true dependency injection (call the already-pure `loadCentralClassificationFixture`/`parseCentralClassificationFixture` directly, or pass an explicit function parameter the test harness supplies), never via a signal that lives in the same process-environment namespace Claude Code's own `env` settings key writes into." `central-classification.ts` already has the right internal seam for this (`parseCentralClassificationFixture` is pure and independently testable against a string, per its own header, `central-classification.ts:59-64`) — the hook's own test-injection choice bypassed the seam that was already sitting right there and went through the shared, session-writable ambient channel instead, for convenience (it mirrors this codebase's existing `CLAUDE_PROJECT_DIR`/`HOME` test-injection pattern, which is legitimate for those two vars because a governed session already has unrestricted write access to everything `CLAUDE_PROJECT_DIR`/`HOME` would let it redirect — there is no privilege being crossed there. This var is different in kind: it redirects which policy the fail-closed gate itself trusts, which is exactly the one thing section 0.4 says a session must never reach).

**Is the remaining shape sound, once the override is removed?** Yes, as the interim stopgap it is disclosed to be — but with one honest caveat that must stay attached to it, not quietly dropped: since `PreToolUse` is not yet wired (`docs/decisions.md`'s 2026-09-07 "S5 activation deferred" row), the committed fixture file itself is also currently reachable by the governed session with no different protection than any other tracked file in this repo — its only real protection today is that an edit shows up as a `git diff` a human/CI would see, exactly the same protection (and exactly the same limitation) as every other part of this already-disclosed, already-ratified "Plane B, never certain" mechanism (`REQUIREMENTS.md` section 0.3). That is not a new defect this pass introduces — it is the same tension S5's own 2026-09-06 ratification row already named and the human already accepted ("the bootstrap ruleset is unavoidably a normal, session-writable file... ratified per section 0.2's own corollary... disclosed, not concealed"). The env-var override is a different, additional hole layered on top of that already-accepted tension, and it is strictly worse than the tracked-file exposure because it leaves no diff, no gate, no test, no trace (red-team N1's own framing, which this seat independently confirms is the correct one). Fixing the override does not need to, and should not, try to also solve the pre-existing "committed fixture is a normal file today" tension — that tension is out of this fix-now round's scope and already carries its own ratified disclosure.

## 2. Disposable stopgap, or calcification risk for S6?

The shape is a good, disposable stopgap. One element of it is not, and must not be copied forward.

`cross-domain-reviewer`'s round-2 report already named this precisely (`s5-cross-domain-round2-2026-09-07.md` section 7, `[SUSPICION][LOW][derived]`): the fixture-loader pattern (versioned/dated/expiring JSON, loaded by a dedicated pure module, pinned by a regression test) is a real, working precedent for S6's eventual central-config-loader shape, and nothing has ruled whether S6 should adopt, generalize, or reject it. This seat concurs it is real, and sharpens it into a concrete, answerable question rather than a general "watch this":

**NOT-COVERED, feeds S6 intake:** Can an in-repo, git-committed JSON fixture ever satisfy `REQUIREMENTS.md` section 0.4 property 2 ("session cannot write it") at all — or is "committed to the governed repository" structurally incompatible with that property, regardless of how many layers of review/pinning/expiry are added on top? A file living inside the repository the governed session has commit access to is, by definition, one the session can eventually write (via a PR, via direct commit access, via exactly the kind of pressure that produced the original hardcoded-array shape this fix-now round replaced). Today's fixture is fine only because it is explicitly disclosed as a stopgap under an already-not-yet-a-security-boundary mechanism (section 0.2's corollary) — the risk is not that S5 shipped this, it is that S6 is the story whose entire job is to deliver section 0.4 for real, and if S6's intake discovers this pattern already built, tested, and "working," the path of least resistance is to harden it in place (better file permissions, a CI check, a second reviewer) rather than to ask whether an in-repo file can ever clear property 2 — which it structurally cannot, since section 0.4 requires the source be unreachable by any credential the governed session holds, and a session with commit access to its own repository always holds a credential reaching a file inside that repository. What would make S6's job harder because this shipped: inheriting the belief that "committed fixture, hardened" is a valid endpoint for centralization, when the requirement text names an endpoint (session holds no credential reaching the source) that a same-repo file cannot reach no matter how it's hardened — only an out-of-repo source (a separate policy-authoring location the governed session's own credentials don't cover) can. This is worth one explicit line at S6 intake now, precisely because the fixture works well enough today that nobody will be forced to ask the question later without a flag planted here.

What should NOT be inherited regardless of the section 0.4 question's answer: the ambient-env-var test-injection idiom in the shipped entry point (section 1 above). If S6 builds its real central-config loader by extending `central-classification.ts`'s shape (plausible — it is a reasonable module to extend), it must not also extend the test-injection pattern that came bundled with it. This is a narrow, mechanical thing to flag explicitly at S6 intake, separate from the property-2 question, because otherwise it is exactly the kind of "it already exists and works" inheritance this seat's mandate exists to catch before it happens by default.

## 3. Blast radius: does it justify a redesign now, or a targeted patch?

Targeted patch. Not a redesign of the trust boundary.

Today, live: `PreToolUse` is unwired (2026-09-07 STATE.md deferred-activation decision) — no real session is gated by this mechanism yet, so the override's exposure against today's actual deployment is 0% of live enforcement. Its exposure against the mechanism's own claimed property, the moment activation happens, is ~100% of the tool/connector-exemption surface (red-team's own measured figure, `s5-fixnow-round2-red-team-2026-09-07.md` N1) — this is a pre-activation-must-fix, not a currently-live leak, and that distinction matters for urgency without changing the verdict: it must be fixed before `PreToolUse` goes live, not before this specific commit lands, but there is no reason to defer it given the fix is small and already scoped.

The four moving parts this mechanism actually contains — allowlist content (AC1), runtime expiry (AC1-c), sticky-halt reconciliation (AC5), and the disclosure/ratification trail — are not redundant with each other. Each closes a distinct, already-demonstrated defect from an earlier round (hardcoded array leading to Issue #90/#92; no expiry leading to this round's whole premise; sticky halt leading to Issue #94/#95). Removing any of the four regresses a real, already-fixed problem. The one part that was never load-bearing to any of those four properties, and should never have existed in the shipped entry point, is the fifth: the ambient-env override. A redesign of the fixture-loading topology (fewer layers, a different data shape, a different module boundary) would not make N2 (unpinned `expiresOn`) or N3 (unlock hint blind to expiry) structurally impossible — those are ordinary test/message-coverage gaps that recur under any config shape unless someone writes the specific assertion/branch for them, and are correctly scoped as their own small, targeted fixes (Issues #100, #101), not evidence the topology is wrong.

## 4. Cost shape: would a structurally simpler shape have made round 2's findings impossible?

One fewer moving part (delete the ambient-env seam, or replace it with true DI) would have made N1 structurally impossible. It would not have prevented N2, N3, or N4 — those are coverage gaps, not shape defects.

This is a narrower and more useful lesson than "collapse allowlist+expiry+reconciliation+override into something simpler": the four legitimate parts are each answering a distinct acceptance criterion and should stay separate (that separation is exactly what let red-team pin down each of N1-N4 individually rather than facing one tangled mechanism). The generalizable rule this seat would put in front of S6 and any future story touching a fail-closed config loader: a production entry point that enforces a security-relevant decision must never read an ambient, session-settable signal (environment variable, unvalidated file in a session-writable path) to decide which policy source it trusts — a test harness that needs a different fixture calls the pure loader/parser directly, or the production code accepts an explicit, narrowly-typed override parameter that only the test harness's own direct import can supply, never one that the runtime's documented `env`-delivery mechanism can also reach. This is a standing convention worth writing down once (a short addition to CLAUDE.md's sensitive-areas guidance, or a new SE ADR rule, is the Manager's/architect's call, not this seat's to mandate unilaterally) rather than re-discovering it component-by-component.

Same locus as `red-team`'s round-2 N1 (`[ISSUE][HIGH][demonstrated]`, filed as GitHub Issue #99, already open) — this seat's contribution is the compliance verdict (a named requirement text is violated, independent of exploitability or activation state) rather than a fresh exploit. 2. **[SUSPICION][MED][derived]** — NOT-COVERED architectural question for S6 intake: an in-repo, git-committed fixture is structurally incapable of ever satisfying section 0.4 property 2 ("session holds no credential reaching the source") no matter how it is hardened, because a session with commit access to its own repository always holds a credential reaching a file inside that repository — only an out-of-repo source clears the bar. No Issue filed (SUSPICION, non-blocking per this project's convention) — recommended as an explicit line at S6/Milestone #24 intake, not left to be discovered mid-build.
3. **[SUSPICION][LOW][derived]** — the ambient-env-var test-injection idiom used for N1 (mirroring this codebase's own `CLAUDE_PROJECT_DIR`/`HOME` precedent, which is legitimate there because the session already holds unrestricted write access to what those two vars redirect) should not be copied into S6's real central-config loader or any future fail-closed config-loading module — the correct test-injection seam is the already-pure `parseCentralClassificationFixture`/`loadCentralClassificationFixture` split (`central-classification.ts:59-64`), called directly by the test harness, never an ambient signal the production entry point honors unconditionally. Non-blocking; a convention worth naming once rather than rediscovering per-module.
4. **[CLEAN][code-traced]** — the remaining shape (committed, dated, versioned JSON fixture; pure parse/validate split from I/O per SE ADR-0002/0003's DI pattern; pinned exact-match regression test; runtime expiry check on every `SessionStart`) is a sound, minimal, disposable interim pattern consistent with this project's own established disclosed-gap-now/close-later convention (S2's deferred config loading, S3's fixture-proven allowlist, S4's residual findings) and requires no topological redesign. Confirmed via direct reading of `central-classification.ts` and cross-checked against `cross-domain-reviewer`'s independent ADR-0021/kernel-purity re-run (`s5-cross-domain-round2-2026-09-07.md` section 3), which found zero collisions across the full 35-ADR catalog.
5. **[CLEAN][derived]** — the four non-override moving parts (allowlist content, runtime expiry, sticky-halt reconciliation, disclosure/ratification trail) are not redundant with each other; each answers a distinct, already-demonstrated defect from an earlier round, and none should be collapsed or removed as part of fixing N1.

## NOT-COVERED / AMBIGUOUS list (architect's work queue)

## Verdict

**APPROVE-WITH-CONDITIONS** on the fixture-loading mechanism's continued existence and shape. The topology should not be redesigned. Conditions, all already scoped as small and already tracked:

1. Remove the ambient-env override from the shipped entry point (`hooks/sessionstart-tool-enum.mjs:238-241`) and replace the test-injection seam with true dependency injection through the already-pure `parseCentralClassificationFixture`/`loadCentralClassificationFixture` split — closes Issue #99 at the architectural root, not just its currently-demonstrated exploit path.
2. Pin `expiresOn` to its exact ratified value (Issue #100) and make expiry a distinct, relay-nameable cause so the unlock hint at expiry is accurate (Issue #101).
3. Add one explicit line to `docs/backlog.md`/S6 intake naming the section-0.4-property-2 question above (Finding 2) — not solved now, but recorded so S6 doesn't inherit this pattern by default.

This is a mechanical patch to the trust boundary's one broken element, not a redesign of it — consistent with `red-team`'s own single-next-action recommendation, reached independently via the compliance/evolution-path axis rather than the exploit axis.
