## Findings, ranked by blast radius (exposure x irreversibility x silence)

### 1. [ISSUE][HIGH][demonstrated] — QA-14 never *sees* bare `#N` citations at all; this diff turns that from a loud hole into a silent one

**Attack.** The story premise is: QA-14 issue check was a stub returning `null`, it is now a real `gh`-backed lookup. I attacked the *denominator*. Before asking whether the lookup is correct: is the set of citations it is asked about complete?

**Scenario.** An agent writes `Closes #120` in a CHANGELOG entry, or `Milestone #23` in `ci.yml`, or `see #999999` in a review report. QA-14 runs. The citation is never matched by any candidate regex, never classified, never counted, and never appears in the output. `summarizeCitations` then prints `PASS: N citation(s), all resolved` — a confident green — having never looked at it.

**Root cause, code-traced.** `src/qa/reference-resolver.ts:56`:

```ts
const ISSUE_CANDIDATE_RE = /\b(?:[\w.-]+\/[\w.-]+)?#\d+/g;
```

The leading `\b` sits before an *optional* group. When the group does not participate, `\b` must match immediately before `#`. `#` is a non-word character, so that boundary only exists when the PRECEDING character is a word character — i.e. exactly the case you do not want (`a#120`), and never the cases you do (`Closes #120`, `(#120)`, line-start `#120`).

Demonstrated (both candidate regexes copied verbatim from source):

```
"Closes #120"                bareRE= [] wordRE= []
"see #120 for detail"        bareRE= [] wordRE= []
"(#120)"                     bareRE= [] wordRE= []
"x #120"                     bareRE= [] wordRE= []
"#120 at line start"         bareRE= [] wordRE= []
"Fixes #120."                bareRE= [] wordRE= []
"[#120]"                     bareRE= [] wordRE= []
"a#120"                      bareRE= ["#120"] wordRE= []
"Issue #120"                 bareRE= [] wordRE= ["Issue #120"]
"owner/repo#120"             bareRE= ["owner/repo#120"] wordRE= []
"PR #120"                    bareRE= [] wordRE= []
"ref: #120"                  bareRE= [] wordRE= []
```

Only `Issue #N` (via `ISSUE_WORD_CANDIDATE_RE`) and `owner/repo#N` are ever classified.

**Exposure: ~54.3% of `#N` occurrences on this diff own scanned scope (390 of 718), basis: measured** — index-overlap of every `#\d+` occurrence against the spans produced by both candidate regexes, over the real files in `git diff --name-only 6f61d44 d05ca33`:

```
DIFF SCOPE: #N occurrences=718, never classified=390 (54.3%)
```

Full tree (excluding `node_modules/`, `.git/`, `adr/`):

```
#N occurrences (scanned files): 3515
  matched by SOME candidate regex (classified):    1677
  matched by NO candidate regex (SILENTLY SKIPPED): 1838  -> 52.3%
  of which "Closes/Fixes/Resolves #N" (CLAUDE.md-mandated form): 7
samples of silently-skipped:
    .claude/settings.json:    ...VED 2026-09-06 (S5, Milestone #23, Is
    .github/workflows/ci.yml: ...on / Issue #87 fix, Milestone #23)
    .github/workflows/ci.yml: ...fest-check (SUR-13, Milestone #23)
    .gitignore:               ...n-report.json # S5 (Milestone #23): h
```

**Current defense, honestly assessed.** None. There is no counter, no NOTE line, no vacuous-pass disclosure for unmatched `#N` text. This is a direct self-violation of the acceptance criterion quoted verbatim in this file own header at `src/qa/reference-resolver.ts:5-6`: "The checker parses this project own house citation style... a checker that silently skips what it cannot parse is a failing checker, not a passing one (QA-16)."

**Is this in scope, and is it a duplicate of #137?** The regex itself is unchanged by this diff, so the HOLE is pre-existing — I state that plainly. It is NOT covered by Issue #137: #137 is entirely about false POSITIVES (basename-only paths over-flagged, ADR-word prose over-flagged, a slash-less cross-repo ref mis-attributed). This is the opposite direction — false NEGATIVES, citations that are never examined. Different defect class, different fix.

What THIS diff does is change the hole character, and that part is attributable. Before `d05ca33`, `issueExists` returned `null` unconditionally, so every citation QA-14 did detect failed closed and the step was red — the gate was loudly, visibly not-working. After `d05ca33`, detected citations resolve green, so QA-14 output becomes a confident `all resolved` computed over a ~46% denominator. The diff converts "obviously broken" into "silently partial." For a CRITICAL-tier change to a gate whose entire purpose is this check, that is the finding.

**Verdict: BREAKS.**

**Named proof-test required before merge** (either; the second is cheap enough to land in this PR):

- `QA-14: a bare "Closes #120" / "(#120)" / "Milestone #23" citation reaches classification, not silently skipped` — a new case in `src/qa/reference-resolver.test.ts` asserting `scanReferences` produces a citation for each of the 10 demonstrated-missing shapes above. Currently fails for 9 of 10.
- OR `QA-14: summarizeCitations discloses the count of #N occurrences that matched no candidate regex` — adopt this repo own existing "disclosed, not silent" pattern (the VACUOUS-PASS + NOTE lines `broken-instrument-gate.ts` and `completeness-claim-checker.ts` already print). This makes the hole loud without changing classification semantics, and is a one-function change.

**Design note for whoever fixes it — do not let this be sold as a one-liner.** The minimal regex correction, moving `\b` inside the optional group (`/(?:\b[\w.-]+\/[\w.-]+)?#\d+/g`), works and is cheap on API cost: I measured distinct local issue numbers rising only 101 -> 116 full-tree, because most missed occurrences repeat numbers already cited via `Issue #N`. But it is NOT sufficient on its own: it would newly feed `Milestone #23`, `Milestone #22`, `Milestone #26` into `verifyLocalIssue`, and GitHub milestone numbers live in a different namespace from issue numbers. A correct fix must distinguish `Milestone #N` from an issue citation, which makes this a real classification-design change — the same reasoning #137 used to justify its own fast-follow scope call.

### 2. [ISSUE][MED][demonstrated] — the entire two-pass wiring in `main()` is untested; a total fail-open mutant survives all 670 tests

**Attack.** The six new tests all target `checkIssueViaGh` in isolation with a fake `Runner`. Nothing tests the thing that actually decides pass/fail in CI: the pass-1 collector -> `issueCache` -> pass-2 resolution chain in `main()` (`src/qa/reference-resolver.ts:337-371`). `main()` is not exported and has no test seam.

**Scenario.** A future refactor, or a careless merge-conflict resolution, changes one line of that wiring to something that always reports success. Nothing in the repo notices.

**Demonstrated — mutation M1.** I replaced `src/qa/reference-resolver.ts:366`:

```ts
    issueExists: (n) => issueCache.get(n) ?? null,
```
with
```ts
    issueExists: () => true, // MUTANT M1: total fail-open
```

and ran the full suite:

```
$ npm test

```

MUTANT SURVIVED. A change that makes QA-14 declare every issue citation valid — including fabricated ones, which is the single non-optional failure shape QA-14 own header acceptance names — is invisible to this repo entire test suite. (File restored; `git status --short` verified clean afterwards.)

**Exposure: 100% of CI runs execute this wiring, 0% of it is covered, basis: measured** (mutation survival on the full 670-test suite).

**Current defense, honestly assessed.** I read the wiring line by line and it is CORRECT TODAY: `?? null` correctly preserves a `false` value (nullish-only), both passes use identical `baseDeps` and identical `scanReferences`, and no classification branch decides WHETHER to call `issueExists` based on its return value, so the pass-1 query set provably equals the pass-2 query set. **Verdict: BREAKS** (as a gate-integrity finding, not a behavioural one).

**Named proof-test required:** `QA-14: main() issue-resolution wiring rejects a fabricated issue citation end-to-end` — extract the two-pass block into an exported, Runner-injected function (e.g. `resolveIssueCitations(fileTexts, baseDeps, repoSlug, runner)`) and assert that a fake runner returning the documented not-found stderr yields a FAIL InstrumentResult. ### 3. [ISSUE][MED][demonstrated] — one un-batched, un-retried, un-cached `gh` call per distinct cited issue, against a 1,000/hr/repo token; exhaustion is indistinguishable from the bug #120 just fixed

**Attack.** `src/qa/reference-resolver.ts:355-358` loops sequentially, one `gh issue view` per distinct number, every run, with no cross-run cache and no batching.

**Measured call volume:**

```
DIFF SCOPE files: 10   distinct issue numbers: 71
FULL-TREE: files scanned = 286   distinct issue numbers = 101
```

**Measured latency** (real `gh`, real network, through `checkIssueViaGh` + `realRunner`):

```
#110=true #111=true ... #119=true
10 sequential calls = 4570ms  (~457ms each)
extrapolated for 101 distinct numbers: 46.2s
```

**Documented ceiling** (GitHub REST rate-limit docs, fetched 2026-09-10): "The rate limit for GITHUB_TOKEN is 1,000 requests per hour per repository." That is a PER-REPOSITORY budget shared by every workflow run, not per-run.

**Scenario.** A normal ship-loop afternoon: 71-101 GraphQL calls per CI run, so roughly 10-14 runs/hour exhausts the entire hourly repo budget — and the QA-14 step is not its only consumer. On exhaustion `gh` returns HTTP 403; `checkIssueViaGh` correctly returns `null`; `verifyLocalIssue` then emits, for every single citation:

> cannot verify (no issue-tracker access) — fails closed, not silently skipped

That is VERBATIM the failure mode Issue #120 exists to eliminate. An operator seeing a red QA-14 with that message has no way to tell "the fix regressed / the token lost its scope" from "we pushed too many times this hour." The gate fails closed (good) but diagnoses itself wrongly (bad), and the blast radius is every CI run for the remainder of the hour, repo-wide.

**Current defense, honestly assessed.** Per-call `timeoutMs: 30_000` is set, so SE-0006 "explicit timeouts on every network call" is satisfied. Within a single run, `issueCache` correctly de-duplicates. That is the whole of the defense: no cross-run cache, no `gh api graphql` batching (all N numbers could be fetched in ONE aliased GraphQL query), no 403/rate-limit-specific message, and no global time budget — worst case 30s x 101 = ~50 minutes of a CI step against a degraded API.

**Exposure: 100% of CI runs make 71-101 API calls, basis: measured.** Probability of exhaustion depends on push cadence, which I did not measure — so I claim the MECHANISM, not a frequency.

**Verdict: BREAKS.**

**Named proof-test required:** `QA-14: a 403/rate-limit stderr is reported as rate-limiting, distinctly from "no issue-tracker access"` — a fake-Runner test asserting `checkIssueViaGh` still returns `null` (unchanged, correct) AND that the surfaced reason names rate-limiting. Plus a named follow-up to batch the lookups into a single `gh api graphql` aliased query, which collapses 101 calls to 1.

### 5. [SUSPICION][LOW][demonstrated] — the `\b404\b` -> `false` branch is unreachable via `gh issue view` in every failure mode I could produce, and is untested

**Attack.** `src/qa/reference-resolver.ts:260` treats any stderr containing a standalone 404 as a positively-confirmed absence. I tried to reach it.

```
{"label":"nonexistent-issue","code":1,"stdout":"","stderr":"GraphQL: Could not resolve to an issue or pull request with the number of 99999999. (repository.issue)"}
{"label":"nonexistent-repo","code":1,"stdout":"","stderr":"GraphQL: Could not resolve to a Repository with the name mohannadrabie/no-such-repo-xyz. (repository)"}

$ gh issue view 1 --repo torvalds/linux --json state
the torvalds/linux repository has disabled issues            exit=1

$ GH_TOKEN=<bogus> gh issue view 120 --repo mohannadrabie/thoth --json state
HTTP 401: Bad credentials (https://api.github.com/graphql)     exit=1
```

`gh issue view --json` goes through GraphQL, which returns HTTP 200 with an error body; it does not emit a bare 404. The only place I could produce one was the REST path (`gh api repos/.../issues/99999999` -> `gh: Not Found (HTTP 404)`), which this code never calls.

**Risk if it ever does fire.** It would fire on a REPOSITORY-level 404, not an issue-level one — meaning every citation in the run would be classified `false` ("Issue #N does not exist in this repository") when the real cause is "the token cannot see this repo." Fail-loud but misdiagnosed, and it would be the second message in this change that lies about its own cause (see finding 3).

**Verdict: UNPROVEN-pending-verification.** I could not construct a real trigger. The next step is a decision, not a fix: either drop the clause as unreachable, or add the test that pins its intent.

**Command that settles it, and who runs it:** a maintainer holding a fine-grained PAT scoped to Contents-only (no Issues) runs `gh issue view 120 --repo mohannadrabie/thoth --json state` and records the exact stderr. If it is not 404-shaped, the clause is dead code.

### 6. [SUSPICION][LOW][code-traced] — zero retries on an idempotent read; SE-0006 asks for bounded retries with backoff and jitter

SE ADR-0006 line 33: "MUST set explicit timeouts on every network call and bounded retries with exponential backoff + jitter; MUST NOT retry non-idempotent operations." `checkIssueViaGh` sets the timeout (`timeoutMs: 30_000`, satisfied) but performs no retry at all. `gh issue view` is a pure read — the one case the MUST-NOT-retry carve-out does not apply to. A single transient 502 or DNS blip on any one of 71-101 calls turns the whole gate red with the misleading "no issue-tracker access" text from finding 3. Zero is technically bounded, so I flag this as tension, not a clean violation.

Related, same line: there is no GLOBAL budget. 30s x 101 calls = ~50 min worst case in a single CI step, with no `timeout-minutes` on the job.

**Verdict: UNPROVEN-pending-verification** (I did not induce a transient failure). Settles as a one-line `timeout-minutes:` on the job plus a single bounded retry, or an explicit accepted-risk line in the residual register.

### 7. [SUSPICION][LOW][code-traced] — `GH_TOKEN` now lives in a job that executes PR-authored code; named as the weakest trust-chain link

## SURVIVES — attacks that failed

### 8. [CLEAN][demonstrated] — command injection via a crafted issue citation: no shell, argv-only, digits-only

I fed `scanReferences` a hostile corpus of 11 metacharacter payloads and traced the exact argv reaching the Runner, additionally passing a poisoned `repoSlug`. Payloads included a command substitution, a backtick substitution, a pipe, an `&&` chain, a `;` chain, an injected `--repo attacker/evil` flag, a 20-digit number, and a leading-zeros number.

```
collected issue numbers: [120]
all are JS numbers, digits only: true
argv: ["gh","issue","view","120","--repo","mohannadrabie/thoth; rm -rf /","--json","state"]
```

`n` is `Number()` of a `(\d+)` capture (`src/qa/reference-resolver.ts:80,85`) — structurally incapable of carrying a metacharacter. `String(n)` and `repoSlug` are discrete argv elements passed to `execFile` (`src/lib/exec.ts:44`), never a shell string; `realRunner` never sets `shell: true`. The poisoned slug is passed inert as a single argument. Nothing reaches a shell. SURVIVES.

### 9. [CLEAN][demonstrated] — a PR number cited as an issue resolves `true`, as the docstring claims

The docstring at `src/qa/reference-resolver.ts:229` asserts "an Issue or PR — GitHub own API does not distinguish the two here." I tested it rather than believing it:

```
$ gh pr list --repo cli/cli --state merged --limit 1 --json number --jq .[0].number
14417
$ gh issue view 14417 --repo cli/cli --json state
{"state":"MERGED"}   exit=0
```

A legitimate `Issue #<pr-number>` citation resolves rather than being rejected. I also confirmed the converse: `gh issue view 10000 --repo cli/cli` returns `{"state":"CLOSED"}` for a real issue, while `gh pr view 10000` rejects it as not-a-PR. SURVIVES.

### 10. [CLEAN][demonstrated] — every inconclusive `gh` failure mode classifies as `null`, never `false` and never `true`

I walked every branch against real `gh`, not fakes. Six distinct failure modes, all resolving to `null` (fail closed):

| Real failure mode | exit | stderr | classification |
|---|---|---|---|
| bad credentials | 1 | HTTP 401: Bad credentials (api.github.com/graphql) | `null` |
| repo not resolvable / no access | 1 | GraphQL: Could not resolve to a Repository with the name ... | `null` |
| issues disabled on repo | 1 | the torvalds/linux repository has disabled issues | `null` |
| timeout / killed subprocess | 124 | (empty) | `null` |
| exit 0, unparseable stdout | 0 | — | `null` |
| `repoSlug === null` | — | runner never invoked | `null` |
| GENUINE not-found | 1 | GraphQL: Could not resolve to an issue or pull request with the number of 99999999. (repository.issue) | `false` (correct) |
| GENUINE exists | 0 | `{"state":"OPEN"}` | `true` (correct) |

Critically, the `true` path requires `code === 0` AND parseable JSON AND a literal `state` key — no `gh` failure mode I could produce satisfies all three, so a FALSE PASS is not reachable. And the not-found message arrives on STDERR with a non-zero exit (verified through `realRunner` own stream separation, not a `2>&1` shell capture), so the `false` branch is genuinely live and not dead code. SURVIVES — this is the strongest part of the change.

### 11. [CLEAN][code-traced] — the job-level `permissions:` override is strictly additive; nothing else in the job is narrowed

GitHub replaces, rather than merges, the workflow-level `permissions:` map when a job declares its own. The previous effective grant for the `ci` job was `contents: read` (`.github/workflows/ci.yml:25-26`); the new job block is `{contents: read, issues: read}` (`ci.yml:40-42`) — a superset, so no step can lose an entitlement it previously had. The `adr` submodule step authenticates with `ADR_REPO_PAT`, not GITHUB_TOKEN, and is unaffected. `actions/checkout` runs with `persist-credentials: false` and needs only `contents: read`. `actions/upload-artifact@v4` uses the Actions runtime token, not GITHUB_TOKEN permissions. The scheduled `runtime-settings-drift` job declares no `permissions:` block and correctly keeps the unwidened file-level default. `GH_TOKEN` is set in the QA-14 STEP `env:`, not job- or workflow-level, so it does not leak into `npm ci` or any other step. SURVIVES. One editorial nit on the comment wording, below.

### 12. [CLEAN][code-traced] — pass-1 and pass-2 are provably symmetric; no citation can bypass the real check via the two-pass split

Both passes call the identical `scanReferences` over the identical cached `fileTexts` (`src/qa/reference-resolver.ts:330-335`, read once up front) with identical `baseDeps`; only `issueExists` differs. I checked whether any classification branch decides WHETHER to call `issueExists` based on state that differs between passes: `classifyIssue` (`:71-91`) short-circuits to `cross-repo-issue` using only `deps.repoSlug`, identical in both; `verifyLocalIssue` (`:93`) calls `issueExists` unconditionally as its first statement; the per-file `seen` dedup in `scanReferences` is deterministic on text. Therefore the pass-1 query set provably equals the pass-2 query set. `issueCache.get(n) ?? null` is correct — `??` is nullish-only, so a cached `false` survives and is not silently upgraded to "cannot verify." SURVIVES. The `?? null` fallback is unreachable-by-construction, which is fine as belt-and-braces.

### 13. [CLEAN][code-traced] — no partial-failure state can produce a green pass

`realRunner` never throws (`src/lib/exec.ts:53-60` catches everything, including ENOENT when `gh` is absent, mapping a non-numeric `e.code` to 1), so no `gh` outcome escapes classification in `checkIssueViaGh`. If `main()` did throw between the passes, the top-level `await main()` (`:379`) surfaces an unhandled rejection and Node exits non-zero, so the step is red. A cancelled or killed run kills the step, red. `process.exit(exitCodeFor(result))` is the only green path and it requires a fully-computed `result`. There is no intermediate state that exits 0. SURVIVES.
