### Attack 1 — exec gate: unprotected binary executed without opt-in / flagged to PASS  [demonstrated]
Probe: checkExtraction(env, spyProvider, judgment, protectedList) with a COPY of node.exe placed as
claude.exe on an unprotected PATH dir; fake home; APPDATA/LOCALAPPDATA at empty fake dirs;
THOTH_CLAUDE_BIN unset. Results:
- default (no opt-in): providerCalls=0, binStatus=FAIL, executed=false, location=unprotected,
  flag=UNVERIFIED-UNPROTECTED, sha256 computed read-only (64 hex). The binary is never executed.
- opt-in THOTH_EXEC_UNPROTECTED set to 1: providerCalls=1, executed=true, still FAIL (version
  mismatch). Fail-closed even when executed.
- near-miss opt-in values 01, true, "1 " (trailing space), " 1" (leading space), 0, empty:
  providerCalls=0 on every one. Only the exact string 1 opts in.
A flagged binary always carries a non-empty reasons entry (UNVERIFIED-UNPROTECTED) so status is FAIL;
overall FAIL (never PASS). SKIPPED only when found.length is 0, which cannot coincide with an executed
planted binary. SURVIVES.

### Attack 2 — classification bypass (make an unprotected path look protected)  [demonstrated]
classifyLocation / classifyBinary against a fake home plus the canonical generated tilde entries:
- mixed-case AppData/Roaming/Claude/claude-code -> protected (canonicalize lowercases, same real dir)
- claude-code/../../evil/... (dot-dot) -> unprotected (dot-dot segment rejected pre-canon)
- packages/Claude_abc123/.../claude-code/... (other pkg) -> unprotected (only pinned publisher listed)
- C:/evil/claude.exe (outside home) -> unprotected (relative() escapes)
- claude-code-evil/... (sibling prefix) -> unprotected (trailing-slash entry blocks prefix spill)
- APPDAT~1/Roaming/.../claude-code/... (8.3 short) -> unprotected (not expanded, fail-closed)
- UNC / verbatim-prefixed protected path -> unprotected (non-home-relative, fail-closed)
- claude-code. and claude-code (trailing dot/space) -> protected (Windows folds to the SAME real
  protected dir, not a bypass)
- junction INSIDE protected dir pointing outside -> unprotected (classifyBinary realpath check escapes)
Every attempt fails closed or resolves to the genuine write-protected real directory. No path lands an
unprotected binary in the protected (executable) bucket. SURVIVES.

### Attack 3 — do the Desktop-root + dev-mods deny rules deny all 6 verbs?  [demonstrated]
Fed the committed shipped-defaults.json rules to the real decide() kernel. For both Desktop roots and
dev-mods, every verb in {write, create, modify, delete, move, rename} on the directory AND on a child
path -> deny by the expected rule id. execute -> allow (execution from a protected dir is the intended
certifier action). Sibling-prefix claude-code-evil -> allow (correctly a different, non-protected dir).
Drift check: committed rules equal generator output (126 protected paths). SURVIVES.

### Attack 4 — do the parent-dir move/delete denies break legitimate session work?  [demonstrated]
Parent rules (appdata, appdata/local, appdata/local/packages, appdata/roaming and deeper ancestors)
are exact-match (no trailing slash), verbs {move, delete, rename} only. Probes: delete
appdata/local/packages -> deny; rename appdata/local -> deny; but write appdata/local/packages ->
allow, and legit child create/delete appdata/local/temp/foo.txt -> allow. Only wholesale
move/delete/rename of the exact protected ancestor directory is blocked; ordinary file churn under
AppData Local is unaffected. No legitimate breakage. SURVIVES.

### Attack 5 — THOTH_CLAUDE_BIN override as a plant vector  [code-traced]
discoverClaudeBinaries adds THOTH_CLAUDE_BIN as an override, but checkOne runs it through the same
classifyBinary; mayExecute = location protected OR optIn (claude-code-write-deny-extract.ts, checkOne).
An override outside the protected list is flagged and not executed without the opt-in (Manager ruling
1). SURVIVES.

## Suspicion (non-blocking)

### S-LOW — layer-1 deny depends on the (unwired) gate + normalizer tilde-handling  [derived]
The deny rules bite only once the PreToolUse gate is wired (today built-but-NOT-WIRED, evaluating only
Bash/MCP tool names, per hooks/pretooluse-kernel-gate.mjs header) and only insofar as the normalizer
presents a write target in the appdata tilde form the rule matches. canonicalizePathTarget keeps a
literal tilde but deliberately does NOT tilde-ify an absolute path (path-canonical.ts header: does not
expand $VAR or ~user), so a Bash write using an ABSOLUTE AppData path relies on POL-05 as the backstop,
not the path rule. This is pre-existing shared behavior of all 120-plus tilde entries, not introduced
by #466, and the certifier own exec-gate (Attack 1, demonstrated) makes the planted-binary attack fail
regardless of layer 1. Recommend (backlog, not blocking): one existing-normalizer test proving an
absolute AppData Claude claude-code write resolves to the appdata tilde target so the new rules bite
the moment the gate is wired. Caps at LOW (derived; pre-existing infra).

## Scariest unproven assumption + go/no-go + next action

- Go / no-go: GO. The attack goal (execute a planted binary without opt-in, or flag to PASS/SKIP) fails

- Single next action: merge #466 as-is; file the S-LOW normalizer-coverage test to docs/backlog.md
