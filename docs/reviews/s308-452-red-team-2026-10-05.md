**Verdict: no-go.** The two-direction logic and the skip/require seam hold, and the tests that CI runs kill every mutant I seeded. The defect is in what "installed" means. On this operator's machine the check certifies a stale standalone binary (2.1.267). The Claude Code that actually runs the sessions K protects is the VS Code extension's bundled binary (2.1.289). Against that binary the same check FAILs. The readiness row prints PASS and never names the binary it read.

## Implicit assumptions, and what happened when I tested them
1. "The binary at `~/.local/bin/claude(.exe)` is the Claude Code that runs the sessions." **Broken on this machine** (finding 1).
2. "SKIPPED cannot be read as PASS by readiness." Holds: readiness fails every non-zero exit (finding 4).
3. "The tests that run in CI, where no binary exists, prove the instrument." Holds: 5 of 5 mutants killed in a CI-like run (finding 5).
4. "`--version` and the extraction read the same file." Holds. PATH is never consulted, so a PATH shim does nothing (finding 6).
5. "The anchored window is the whole write-deny list." Unproven: the same path shapes appear outside the window (finding 3).

## Findings (ranked by exposure x irreversibility x silence)

### 1. [ISSUE][HIGH][demonstrated] BREAKS: the check certifies a stale standalone binary, not the Claude Code that runs the sessions
**Scenario.** The human runs `npm run qa:k-readiness` to activate K. `locateClaudeBinary` (src/qa/claude-code-write-deny-extract.ts:29-33) looks at only three places: `THOTH_CLAUDE_BIN`, `~/.local/bin/claude.exe` and `~/.local/bin/claude`. On this machine, `~/.local/bin/claude.exe` is a native install last written on Sep 9, and it reports 2.1.267, which matches the judgment pin. Every Claude Code process actually running here is the VS Code extension's bundled binary at `~/.vscode/extensions/anthropic.claude-code-2.1.289-win32-x64/resources/native-binary/claude.exe`, and that binary is 2.1.289. This session itself runs with `CLAUDE_CODE_ENTRYPOINT=claude-vscode`. The readiness row goes green. K activates against judgments made for a version nobody runs. The version pin exists to catch a CLI update, and it is silently defeated: the extension updated and the standalone binary did not.

**Current defense, assessed honestly.** The plan's guarantee that the check "queries the SAME binary the extractor read" holds, and the instrument logic is correct: pointed at the right binary, it FAILs. The flaw is the discovery step. Three hard-coded locations cover only the standalone native install. The output names a version but not a path, so a human reading `PASS ... version 2.1.267` has no prompt to ask "is that the Claude Code I use?" Other installs fail closed, because readiness gets exit 3 and marks the row FAIL: npm-global, Homebrew, or the extension only. The false PASS needs a stale standalone binary next to a newer real one. That is exactly this machine's state.

**Exposure:** ~100% of K-readiness runs on this project's operator machine (3/3 running claude.exe processes are the 2.1.289 extension binary; the check reads 2.1.267). Basis: measured.
**Irreversibility / silence:** K activates on a false certificate. Nothing prints a warning. 2.1.289's extraction differs from the judgment, and the human has not judged that difference.

**Required before merge (named failing test):** `CC-extraction-covers-judged/every-installed-binary-checked`. Fixture: an isolated HOME that holds `~/.local/bin/claude(.exe)` at the judged version plus `~/.vscode/extensions/anthropic.claude-code-<v>-<plat>/resources/native-binary/claude(.exe)` at a different version or with an extra entry. Expected: FAIL, with the final line naming every binary path checked. Suggested fix, the implementer's call: enumerate every known install location. That means `~/.local/bin`, the newest `~/.local/share/claude/versions/*`, the VS Code, VS Code Insiders and Cursor extension `native-binary` dirs, and `claude` resolved on PATH. Require each one found to PASS, and print the path(s) in the final line. Alternatively, make readiness require an explicit `THOTH_CLAUDE_BIN` that names the binary K sessions use, and echo it.

### 2. [SUSPICION][LOW][code-traced] UNPROVEN: the `THOTH_CLAUDE_BIN` test override is honored in production and inherited by readiness
**Scenario.** `THOTH_CLAUDE_BIN` is the first candidate (claude-code-write-deny-extract.ts:31). Readiness spawns the CLI with the parent environment (k-readiness.ts:50, `spawnSync` with no `env` option). If an operator left it exported from debugging, or an agent session runs readiness with it set, the check certifies any binary. An older copy of a real claude.exe passes both the version pin and the extraction. The PASS line does not show which file was read.
**Current defense.** None beyond the human reading the version number. The override is documented only as "used by tests".
**Exposure:** unknown. Basis: assumption, so LOW; recommendation: measure it. **Named test:** `CC-extraction-covers-judged/final-line-names-binary`, which asserts that the PASS/FAIL line contains the binary path, and marks the source when it came from `THOTH_CLAUDE_BIN`. The fix for finding 1 likely covers this one.

### 3. [SUSPICION][LOW][demonstrated] UNPROVEN: the extraction covers one anchored ~9.3 KB window, and both sides can shrink together
**Scenario.** "Every write path the binary knows" is really "every entry, in three string shapes, inside one function window". That window runs from the anchor minus 6000 bytes to `bareGitRepoScrubPaths.length=0`. The judgment file was built from the same extraction. If a future version moves some protected entries into another helper, or writes them in another shape, the extraction drops them. If the human then re-judges from that extraction, the judgment drops them too, and both directions pass.
**Evidence (raw, measurement script in the session scratchpad, read-only):**
```
.local/bin/claude.exe        {"anchor":1,"endMark":1,"windowBytes":9326,"projShapeInWindow":18,"projShapeOutsideWindowDistinct":["settings.local.json",".git","ide","settings.json","worktrees","commands","skills","CLAUDE.md","rules","workflows"]}
vscode 2.1.289 claude.exe    {"anchor":1,"endMark":1,"windowBytes":9315,"projShapeInWindow":18,"projShapeOutsideWindowDistinct":["settings.local.json",".git","commands","agents","skills","ide","settings.json","CLAUDE.md","rules","worktrees","workflows"]}
```
The `(x,".claude","<name>")` shape occurs outside the window, including `rules`, `CLAUDE.md`, `worktrees` and `ide`, which are not in the judged project list. I have not shown that any of them is sandbox write-denied. They may be ordinary reads. That is why this finding is UNPROVEN and not BREAKS.
**Current defense.** The version pin forces a human re-judgment on every update, and editing the judgment file is a CRITICAL-tier protected-surface change. Both are real defenses against a silent shrink. Neither checks the window's scope.
**Exposure:** unknown. Basis: assumption, so LOW. **Named test:** `CC-extraction-covers-judged/out-of-window-shapes-accounted`. Every distinct `.claude` path shape found anywhere in the binary is either in the judgment or in a reviewed "not a write-deny site" list. A new one FAILs.

### 6. [CLEAN][demonstrated] SURVIVES: `--version` and the extraction read the same file; a PATH shim or a duplicate anchor does nothing
`checkExtraction` resolves `binary` once and passes it to both `versionProvider(binary)` and `readFileSync(binary)`. `execFileSync` runs with no shell, and PATH is never consulted, so a `claude` shim on PATH that prints the pinned version is irrelevant. Its only effect is the blind spot in finding 1. The extractor takes the first `indexOf(ANCHOR)`, so I tested for a stale duplicate anchor: the anchor and the end mark each occur exactly once in both binaries (measurement under finding 3).

### 7. [CLEAN][demonstrated] SURVIVES: version strings with suffixes, timeouts and throws
`parseClaudeVersion("2.1.267-beta.1 (Claude Code)")` returns `2.1.267`, so a suffixed pre-release would match the pin. Set equality still runs regardless, so a pre-release whose list differs still FAILs. `"2.1.2670"` returns `2.1.2670`, which is greedy and correct. A timeout or throw from `--version` (10 s bound) or an unparseable string gives FAIL; mutant M5 confirms a test covers it. A slow cold start on a large binary under antivirus scanning fails closed and loudly, not silently.

## Single scariest unproven assumption
The binary the check reads is the binary that runs the sessions. On this machine that is false today, measured. Every other guarantee in this change sits on top of it.

## Go / no-go
**no-go.** One HIGH backed by demonstrated evidence (finding 1). **Single next action:** write the failing test `CC-extraction-covers-judged/every-installed-binary-checked`, then widen `locateClaudeBinary` to every known install location, require each one found to PASS, and print the paths in the final line. Separately, before K activates, the human re-judges for 2.1.289. Its extraction adds `localSettings` and `projectSettings`, which look like setting-source names caught by the string-array heuristic. Judging them is the human's call.

## Editorial (verdict-neutral)
- Plan step 9 ("readiness row runs ... with THOTH_REQUIRE_CLAUDE=1") does not match k-readiness.ts, which inherits the environment and fails exit 3 anyway. Either drop the sentence or set the flag in the row.
- The plan's "It queries the SAME binary the extractor read (locateClaudeBinary), not whatever `claude` is on PATH" is true, but it presents a design trade-off as a safety property. The trade-off is that PATH and the extension binaries are never examined.
- Cross-domain pointer, not my lane: ADR-0010 restricts `.skip`. The conditional `t.skip` in `installed-live` copies an existing pattern (`CC-installed-extraction-fully-judged`) and carries a reason. `cross-domain-reviewer` owns whether that needs a recorded exception.
