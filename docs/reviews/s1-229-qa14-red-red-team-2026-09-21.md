## Findings, ranked by blast radius

### 1. [ISSUE][MED][demonstrated] A rename *with an edit* into an append-only path exempts the file's entire body

**Scenario.** A document that QA-14 currently fails on is moved with `git mv` into `docs/reviews/`
(the same mechanism applies to `CHANGELOG.md`, `docs/decisions.md`, `docs/decisions-archive.md` and
`docs/REVIEW_LOG.md`) and one line of it is edited in the same commit. Git detects the rename, so
the diff section carries a new-side header for the append-only path but only **one** added line.
`buildScanTexts` therefore returns just that one line as the scan text. The rest of the file —
including its failing citation — is never read.

**Demonstrated.** In the scratch repository: an 82-line document under a non-append-only path
containing one malformed ADR id.

- Before the rename: `FAIL: 1 of 1 citation(s) failed to resolve`, exit 1, the failure line naming
  the original path.
- Same content, moved under `docs/reviews/` with its header line reworded, one commit:
  `VACUOUS-PASS: 0 citations found in the scanned text`, **exit 0**.
- The scan text computed by `buildScanTexts` for the destination was the 19-byte edited header line
  and nothing else (probed directly against the shipped module).

**Current defense, honestly assessed.** There *is* a test for the adjacent case —
`src/qa/reference-scope.test.ts:479` pins that a **pure** rename (no hunks, 100% similarity) into an
append-only path is scanned whole and exits 1. That case fails closed because git emits no
old-side/new-side headers at all. The moment one byte changes, git emits the headers and the
protection disappears. `src/qa/reference-scope.test.ts:761` exercises a rename-with-an-edit through
`parseUnifiedDiff`, but its destination is an ordinary path, so the append-only branch is never hit.
The combination — rename, with an edit, destination append-only — is the one square of the grid with
no test.

This also **falsifies the recorded decision**. The newest row of `docs/decisions.md`, item (e), is
the QA-16-mandated statement of what QA-14 no longer checks. It names two classes and then asserts
"Nothing a diff adds is exempt in either case." The whole body of a file that the diff places at a
new append-only path *is* content the diff adds at that path, and it *is* exempt. The module header
at `src/qa/reference-scope.ts:32` likewise lists a pure rename with no hunk among the fail-closed
cases, and is silent on the rename-with-an-edit.

**Exposure: ~0% of commits (0 of 258), basis: measured.**
`git log --all --diff-filter=R --name-status -M` over the full history, filtered to destinations in
the append-only set, returns zero. This shape has never occurred in this repository. That is why
this is MED and not HIGH: it is a complete defeat of the gate for the affected file, silent and
permanent (append-only records are never re-read in diff mode), but nothing in the project's real
history triggers it.

**Named proof-test required.** In `src/qa/reference-scope.test.ts`, a test named
"a rename WITH an edit into an append-only path scans the destination whole" — real-git fixture,
move a multi-line document carrying a bad example into `docs/reviews/`, edit one line, assert the
entry point exits 1 and names the destination. The natural fix is one condition in
`buildScanTexts`: when the diff section that produced a file's added lines had a **different** old
path, treat the file as unattributable and scan it whole.

### 2. [ISSUE][MED][demonstrated] The move rule launders a *currently failing* citation to green

**Scenario.** QA-14 reports a failing citation on a line of a whole-file-scanned living document.
Instead of rewording it, the author deletes that line and pastes it verbatim into `CHANGELOG.md`
(or any other append-only record) in the same commit. The removal is from a file this run scans and
that exists on disk, so `moveLicences` issues a licence; `newText` spends it and drops the added
copy. The bad citation is still in the repository, now in a file diff mode will never read again.

**Demonstrated.** Baseline commit, a living document with one malformed ADR id:
`FAIL: 1 of 1 citation(s) failed to resolve`, exit 1, naming that document. Next commit, the line
deleted from it and appended verbatim to `CHANGELOG.md`: `VACUOUS-PASS: 0 citations found`,
**exit 0**. One commit turns a red gate green with nothing fixed.

**Current defense, honestly assessed.** The multiset rule and the removal-source restriction are
both real and both hold (see the CLEAN list — I could not break either). The gap is not in the
mechanism, it is in the *claim*. The module header at `src/qa/reference-scope.ts:24` says the
removal-source restriction "closes the laundering path". It narrows it; it does not close it. The
build report section 4 discloses the neighbouring case — a licence from a file that was never
checked at base — and argues the line already existed in the repository. The case above is different
and undisclosed: the line **was** checked at base and **was failing**, and the move is what makes it
stop failing. Build report section 4 in fact records a line moved out of a scanned living file into
`CHANGELOG.md` exiting 0 as a deliberate control, so the behaviour is known; what is not recorded
anywhere is that this control is also the exploit, and it is precisely the shortcut available for
the red master this story exists to fix.

**Exposure: ~2.1% of commits (5 of 240), basis: measured** for the enabling shape; the harmful
subset is **not** measured. I ran the shipped `parseUnifiedDiff` and `isAppendOnlyRecord` over every
non-merge commit in the repository (240 of 258 diffable): 12 commits (5.0%) contain at least one
added line in an append-only record that the move rule would license, and 5 of those (2.1%) are
licensed by a removal from a **different, whole-file-scanned** file — the exact laundering shape.
The real instances are reviewers quoting into a review report the source line they are removing
(lines out of `src/qa/reference-resolver.ts`, `hooks/sessionstart-tool-enum.mjs`,
`hooks/userpromptsubmit-halt-relay.mjs`, `src/policy/normalizer/shell.ts`). Whether any moved line
carried a *failing* citation is not something I measured, so the harm rate is unquantified and this
stays MED.

**Named proof-test required.** In `src/qa/reference-scope.test.ts`, a test named
"the move rule does not license an added line whose source removal came from a whole-file-scanned
living document". If the Manager prefers to keep the current semantics, the honest alternative is to
delete the "closes the laundering path" sentence at `src/qa/reference-scope.ts:24`, add this case to
the QA-16 statement of what is no longer checked, and register it as a residual. Either resolution
is fine; leaving the claim as written is not.

### 3. [SUSPICION][MED][code-traced] Pre-existing: an unresolvable non-zero base ref is a silent vacuous pass

`resolveChangedFiles` returns null when `git diff --name-only` throws for any reason other than the
zero-SHA sentinel, and `main()` turns that into `VACUOUS-PASS: No diff available`, **exit 0**.
Demonstrated with a fabricated 40-hex base ref against the real repository. This is the single
largest fail-open in the gate, and it is **untouched by this diff** (`src/lib/git.ts` has an empty
diff; the branch in `main()` predates the story). The new code does not widen it: the `diffText`
failure path inside `buildScanTexts` falls back to whole-file scanning, which is strictly safer. It
is also not reachable through the current CI wiring — both triggers supply real SHAs and the
zero-SHA case is handled separately (see CLEAN items 24 and 25). Recorded as a labelled pre-existing
note, not a blocker for this story, and not filed as a new Issue.

### 4. [SUSPICION][LOW][demonstrated] The mirror cut is O(depth x filesize) down the nested-snapshot chain

`collectMirrorSpans` recurses into each nested scope snapshot and `objectMembers` re-scans that
level's entire subtree, so total work grows with depth **times** file size. Measured on synthetic
states: depth 17 / 395 KB = 32 ms; depth 34 / 1.0 MB = 125 ms; depth 68 / 2.9 MB = 806 ms;
depth 136 / 9.6 MB = 4.8 s; depth 272 / 34 MB = 35 s. On the real file today (212 KB, chain depth
17) it is **22.7 ms** — a non-issue now. The reason to record it: the chain grows one level per
story and each level carries its own catalog snapshot (the 18 snapshots are 83% of the current file,
212 KB in, 35 KB out), which is the same cost shape as the prior quadratic CI-gate finding (Issue
247). Suggested threshold rather than a fix: if `docs/.maat-state.json` passes ~1 MB or the chain
passes depth 40, re-measure.

### 5. [SUSPICION][LOW][demonstrated] Two duplicate mirror keys in one object are both cut

`objectMembers` collects duplicates deliberately, so if the mirror key appeared twice in one object
both values are removed, including authored text in the shadowed one. Demonstrated on a
hand-constructed string. Not reachable while the file is written by `JSON.stringify` (which cannot
emit duplicate keys); only a hand edit could produce it. Noted because the build report's own
argument for choosing the tokenizer over parse-and-reserialize is duplicate-key safety, and the
tokenizer is not duplicate-safe for *this* key specifically.

### 6. [SUSPICION][LOW][demonstrated] Symlink behaviour under an append-only directory: UNPROVEN-pending-verification

I attempted a symlink under `docs/reviews/`; this Windows checkout stored it as a regular file
(mode 100644), so the real symlink path (mode 120000, blob content = the target path) was never
exercised. The run exited 1, but for the wrong reason. **Settling command, on Linux or with
`core.symlinks=true`:** create a real symlink under `docs/reviews/` pointing at a document holding a
bad example, commit, and run the entry point against the previous commit; confirm exit 1. Anyone on
a Linux runner can do this in under a minute. I did not verify it, and I am not claiming it breaks.

### Q1 — Can a bad citation be laundered through the moved-line rule?

**Yes, in exactly one way (finding 2); every other route I tried failed closed.** Demonstrated
outcomes, one line each:

| Attempt | Outcome |
|---|---|

| Remove a line from a file under `docs/reviews/`, add it to `CHANGELOG.md` | GREEN; already disclosed in build report section 4 (the line was never checked at base), so not counted separately |
| Multiset abuse: 3 identical adds, 1 removal | RED, exit 1; probe confirms 2 of the 3 lines survive into the scan text |
| Removal from an unscanned test file | RED, exit 1 |
| Removal from the generated mirror in `docs/.maat-state.json` | RED, exit 1 |

| A very long single added line (2 MB) | Parsed in 1.5 ms, no hang |

### Q2 — Can a path be made to miss the diff parser and fail open?

**Once (finding 1). Everything else I threw at the parser fell back to a whole-file scan.**

| Attempt | Outcome |
|---|---|
| Rename **with an edit** into an append-only path | **GREEN — finding 1** |
| Pure rename (no hunks) into an append-only path | Whole file, exit 1 |
| Content lines inside an added block shaped like file headers, a hunk header, and a no-newline marker, all at once | Exit 1, **both** planted bad citations reported against the right file — the hunk-count parser is not spoofable this way |
| A hunk header claiming about a billion lines with a one-line body | Terminates in 0.1 ms, no hang, no crash |
| Append-only path containing a space | Parsed correctly (the tab git appends is trimmed), exit 1 |
| NUL byte in an append-only record (git renders it binary, no headers) | Whole file, exit 1 |
| Mode-only change | No hunks, no added entry, whole file |
| Submodule pointer | Excluded upstream from the scannable list, unchanged by this story |
| Symlink | UNPROVEN on Windows — see finding 6 |
| Combined merge-commit diff | Not reachable: the entry point always runs a three-dot `git diff`, which never emits one. The parser would produce an empty added list for such a section, so a future caller feeding it merge-show output is a fail-open waiting; today it cannot be reached |
| Three-dot vs merge-base mismatch | None: the name-only call and the text call use the same three-dot range, runner and working directory |
| Zero-SHA / force-push sentinel | Full-tree fallback, `FAIL: 182 of 5922`, exit 1 — fails closed, loudly |
| Non-default git prefix or colour config | Code-traced only: a non-default prefix makes the header reader return "cannot attribute", which routes to whole-file. Stricter, never a pass. Carried as follow-up F2, and I agree with that disposition |
| Diff text larger than the runner's buffer | Buffer is 64 MB; this PR's own diff text is 481 KB. Overflow throws, and the read is wrapped in a catch that routes to whole-file. No vacuous path |

**CI wiring — does the real pipeline reach the scoped path?** Yes. The checkout runs at
`fetch-depth: 0` (the comment on that line names QA-14 as a reason). The diff-refs step supplies the
pull-request base and head SHAs on PR events and the before/after SHAs on pushes to master, and the
QA-14 step passes both straight to the entry point. I confirmed against real run logs rather than
assuming: a recent pull_request run and two recent push-to-master runs each printed a real diff-mode
result line (`FAIL: 26 of 1412`, `FAIL: 30 of 1886`) with **no** zero-SHA note — so changed-file
resolution against those refs demonstrably works on both event types, and `26 of 1412` matches the
build report's own leg-1 measurement exactly. The one thing no CI run has yet exercised is the diff
**text** call against those same refs (the branch is not merged); it uses the identical refs, runner
and working directory as the name-only call that demonstrably works, and its failure mode is
whole-file, so I record this as reached rather than at risk. It settles itself on the first master
run after merge: the QA-14 line will show a much smaller citation total than the 1412/1886 above.

### Q3 — Does dropping the generated mirror let authored text hide?

**No, on the real file, proven by instrument rather than by eye.** I ran the strip over the
committed `docs/.maat-state.json` and compared every non-mirror leaf of the parsed input against the
parsed output: **162 leaves compared, 0 differences**, every mirror value nulled, output still valid
JSON, 22.7 ms. (My first pass appeared to show two authored values lost; that was my own harness
comparing decoded strings against raw JSON text with escaped quotes in them. I re-ran it
escape-aware and it is clean. Recording the false alarm because the correction is the evidence.)

Hostile-input battery against the tokenizer — 15 shapes, none threw, none hung, and every one that
was not an exact object-valued mirror key **fell back to scanning**: the mirror key as a string, as
an array, as null; nested under an unrelated key; a string value containing the literal text of a
mirror object; a value containing an escaped quote followed by braces; a key spelled with a unicode
escape (**not** stripped — escapes stay unresolved exactly as the header claims); a key with an
escaped quote in it; the chain key as an array; a top-level array; malformed JSON; JSON with
comments; a trailing comma; a BOM prefix. The only text that hides is a second, duplicate mirror key
(finding 5), which a machine-written file cannot produce.

**Is the ~65-line tokenizer a liability? It is correct, but it is the 50 lines I would trade away.**
The stated benefit over parse-delete-reserialize (~15 lines) is that a duplicate key cannot hide
text and no escape is decoded into or out of a citation. Measured against the real artifact: the
file is machine-written by `JSON.stringify`, has 162 leaves and no duplicate keys, and cannot
acquire one without a hand edit. The simpler design gets the same safety property for two lines:
parse, delete the mirror at the root and down the chain, re-serialize, and **fall back to scanning
the file whole if the round-trip loses any byte you did not cut**. Given the human's stated
preference for simplicity over polish, that trade is worth offering. It is a judgement call, not a
defect — I am not blocking on it.

**The ~75-line diff parser is justified, and I proved it.** The header-spoof attack above is exactly
what a prefix-matching parser would fall for, and the hunk-count design defeats it; the
space-in-path case needs the tab handling; the no-newline marker needs its own skip. There is no
meaningfully simpler safe version. One cheap suggestion: pin the parser's assumptions at the call
site with explicit no-colour, no-external-diff and explicit-prefix flags — that is follow-up F2, and
it would convert a class of surprising red into no red at all.

## Scariest unproven assumption, and the call

The scariest unproven assumption is **that "which text the gate scans" is fully described by the two
classes the decision row names.** Two of my attacks landed outside both of them, one of them in a
single commit with no cleverness required, and neither was caught by 38 tests that were written
specifically for this mechanism. The mechanism itself is sound and fails closed nearly everywhere I
pushed it; the *enumeration of its exemptions* is what is incomplete, and that enumeration is what
QA-16 asks this project to keep honest.

**Go.** No HIGH finding, no crash, no hang, no vacuous pass reachable through the real CI wiring,
the living-document guarantee holds under mutation, and the mirror cut is provably surgical on the
real artifact. The two MED findings are narrow, measured, and each maps to exactly one named failing
test — open findings 2, failing tests 2. Ship, with those two tests and the decision-row amendment
filed as Issues before they are forgotten.
