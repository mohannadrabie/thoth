## Verdict: NO-GO (one HIGH, demonstrated)

The certified-set and remedy logic holds: no binary can PASS without its full judgment, and #466's exec gate is unchanged. The census has a blind spot, demonstrated on the pinned 2.1.289 binary. It drops project-level `.claude/agent-memory` and `.claude/agent-memory-local`, and loses user-level `ide`. It also labels `ide` as "project" even though every 2.1.289 site of that shape is home-rooted. The census's only job in a1 is to make the human's a2 paste complete, and right now it cannot. The fix is small: widen the first-argument pattern, flag home-rooted sites, and add one test.

## Attacks, ranked by exposure x irreversibility x silence

### 1. [ISSUE][HIGH][demonstrated] The census misses real out-of-window `.claude` shapes on the pinned 2.1.289 binary (Issue #477)

**Assumption broken.** "A `.claude` path built outside the window is a `(<bare id>,".claude","<name>")` call, and the user-level shape always calls the window's getter directly." In the shipped code (`src/qa/claude-code-write-deny-extract.ts`, `scanWholeBinary`), the project regex needs a bare word-character identifier as the first argument and `)` right after the name. The user regex needs `(<window getter>(),"<name>")`.

**Scenario.** In a2 the human runs the extractor CLI on the 2.1.289 extension binary and pastes `projectAnywhere` and `userAnywhere`. The judgments are built from that paste. Measured on the 2.1.289 binary (read-only probe, scratchpad `census2.ts`; broadened pattern = any non-quote, non-comma first argument with an optional `()`, name followed by `,` or `)`):

```
== ~/.vscode/extensions/anthropic.claude-code-2.1.289-win32-x64/resources/native-binary/claude.exe
 shipped projectAnywhere: .git,CLAUDE.md,agents,commands,hooks,ide,launch.json,loop.md,output-styles,routines,rules,scheduled_tasks.json,settings.json,settings.local.json,skills,workflows,worktrees
 broadened names: 21; missed by shipped census: 4
   MISSED agent-memory (NOT judged)  e.g. oe(),".claude","agent-memory",
   MISSED agent-memory-local (NOT judged)  e.g. oe(),".claude","agent-memory-local",
   MISSED local (NOT judged)  e.g. P(),".claude","local")
   MISSED state (NOT judged)  e.g. Tt(),".claude","state")
```

The same 4 are missed on the local CLI (2.1.267), via `Q()` and `Dq()` bases.

Context for the material miss (scratchpad `roots.ts`, 2.1.289): `switch(n){case"project":return je(oe(),".claude","agent-memory",r)+Ye;` and `return je(oe(),".claude","agent-memory-local",e)+Ye`. These are the project-scope and local-scope subagent memory directories. Claude Code loads these into a subagent's context, the same class of path as `.claude/agents/`, which is already protected. Neither name is in the judgment file or on the protected list. (`local` and `state` turn out to be home-rooted, `p(P(),".claude","local")` and `_e(Tt(),".claude","state")`, and are judged at user level. They still show that the pattern is blind to call bases.)

User level: on 2.1.267, `~/.claude/ide` is `mxe(Se(),"ide")`, so `census:user:ide` appears. On 2.1.289 it is `let e=we(),r=[_m(e,"ide")]`, with the config dir held in a variable (scratchpad `ide2.ts`). The census does not emit `user:ide` on 2.1.289. Its `userAnywhere` lacks `ide` (scratchpad `vv.ts` output), while the 2.1.267 census has it. So the version-to-version drift the census exists to catch is itself invisible to it.

**Current defence.** A disclosed limit in the code comment: "a path built any other way (a join with several segments) is not seen." It covers only multi-segment joins. A call or member base (`(oe(),".claude",...)`, `(Tt(),".claude","state")`, `(e.workTree,".claude","settings.json")` on 2.1.251) and a variable-held config dir are not disclosed. Tests: `CC-census/*` use only the bare-id fixture `G(Ml(Ie,".claude","ide"),!0)`, so they cannot see this.

**Exposure:** ~100% of a2 census runs against the pinned 2.1.289 binary. 4 of 21 project-shape names (19%) are missed, plus user `ide`. Basis: measured (read-only probe of the installed 2.1.289 and 2.1.267 binaries). Irreversibility: a missed name becomes a silent hole in the shipped K deny set until someone re-spikes by hand. Silence: total, because the census reports a clean superset.

**Verdict: BREAKS.** Required failing test before merge: **`CC-census/call-and-variable-base`**. A fake binary contains out-of-window `(oe(),".claude","agent-memory",r)`, `(Tt(),".claude","state")` and `let e=Se(),r=[_m(e,"ide")]`. Assert that `agent-memory`, `state` and `ide` each appear in the census. The variable-base case may instead be satisfied by a reported "unclassified config-dir site" line, so that it surfaces rather than being silently dropped. Fix sketch: allow the project first argument to be an identifier, member chain or zero-arg call, and accept `,` or `)` after the name.

### 2. [ISSUE][MED][demonstrated] The census's user/project label comes from the shape, not the root, so `ide` is reported as project but is home-rooted (Issue #478)

**Scenario.** On 2.1.289, every `(x,".claude","ide")` site has a home root (scratchpad `ide2.ts`): `_m(TO.homedir(),".claude","ide")`, `_m(n,".claude","ide")` with `n` = USERPROFILE, `_m("/mnt/c/Users",g.name,".claude","ide")`, and `fge(h,".claude","ide")` with `h` = windowsUserProfile. The census reports this only as `census:project:ide`, because `user:ide` is lost per finding 1. The plan (section 5 table, line 53) and the prep doc's approved ruling then protect `.claude/ide/`, the project root. Claude Code never reads that path. The prep doc's own evidence for the ruling (`docs/plans/s308-463-464-prep-2026-10-06.md` line 48) is "`~/.claude/ide/` holds 5 lock files". `~/.claude/ide/` is not on the protected list (`grep -n "ide/" src/qa/protected-path-list.ts` returns nothing). After a2 the readiness row goes green, the protected-entries loop passes on `.claude/ide/`, and the measured lever stays writable.

**Current defence.** None in a1. The label is by construction. The a2 data follows the label.

**Exposure:** 100% of 2.1.289 `ide` sites, 4 of 4 home-rooted. Basis: measured. This is MED rather than HIGH because the wrong-root protection is a2's data, not a1 code. a1's contribution is the misleading label.

**Verdict: BREAKS.** Required failing test: **`CC-census/home-rooted-project-shape`**. A fake binary has `(Os.homedir(),".claude","ide")` and `(n,".claude","ide")` outside the window. Assert the census flags the site as home-rooted or user (or at minimum reports it under both labels), and that a judgment of `ide` in projectOutsideWindow with path `.claude/ide/` alone does not clear it. In a2, add a data check that `ide` resolves to `~/.claude/ide/` on the protected list.

### 3. [ISSUE][MED][code-traced] "Judgments change only through the applier" has no instrument behind it (Issue #479)

**Assumption broken.** "The delta file is the committed, human-approved record, and the judgment files equal base plus applied deltas."

**Evidence.**
- `applyFiles(deltaPath, ...)` in `src/qa/judgment-apply.ts` reads any path with `readFileSync(deltaPath)`. Nothing checks that the delta is tracked or committed, or that it lives under `docs/qa/judgment-deltas/`.
- `grep -rn "judgment-deltas" src` returns nothing: no test replays committed deltas against the judgment files. A hand edit to `docs/qa/claude-code-write-deny-judgment.json`, for example flipping an entry to residual or adding an entry, passes every JA-applier test and every structure test.
- The applier has no modify or remove operation, because conflicts are refused. The first legitimate re-judgment can only be done by hand, which is exactly the act the ruling forbids.

**Scenario.** A later re-judge PR edits the JSON directly, or applies an uncommitted scratch delta. The PR diff shows a judgment change with no matching committed delta, and no check fails.

**Exposure:** every future judgment change. Basis: counted in code (zero readers of judgment-deltas). The reviewer still sees the JSON diff, which is why this is MED rather than HIGH.

**Verdict: BREAKS** (as a claim; the applier itself works). Required failing test: **`JA-replay/committed-deltas-reproduce-judgments`** (lands with a2's first delta). Apply every committed delta file under docs/qa/judgment-deltas/ in order onto the recorded base and assert byte-equality with both committed judgment files. Related: #475 (app-security), which puts the applier and the delta dir on the protected list. That is a different defect; this one is not a duplicate of it.

### 4. [ISSUE][LOW][code-traced] A versions/ entry that IS the local-bin binary is still "prune", against the plan's rule

Plan 6.1.1 says "uncertified = a versions/ entry whose path is not also the local-bin binary". The code (`certifyBinary`: `if (source === "versions") return { certified: false, ... }`) has no such condition, and discovery dedups on the lexical `resolve(path)`, which does not follow symlinks. On POSIX the native installer's `~/.local/bin/claude` is a symlink into `versions/<v>`. If that CLI is at a non-judged version or has a gap, the versions entry's remedy is "prune: delete versions/<v>", which is the live CLI's target. Following it leaves `claude` dangling. On this machine it is harmless: `~/.local/bin/claude.exe` and versions/2.1.267 are a byte copy (sha256 prefix 23dde2a47cf1d7d9c4a2 for both).

Exposure: 0% of runs on this machine. Basis: measured. POSIX consumers are an assumption. Test: **`CC-cert/versions-entry-is-local-bin-target`**. Symlink local-bin to versions/X, then assert versions/X is certified, or that its remedy names the CLI update, not delete.

### 5. [ISSUE][LOW][demonstrated] First-seen dedup lets an obsolete-dir classification override a PATH entry (ruling 2: PATH is certified)

### 6. [ISSUE][LOW][code-traced] The applier moves the version fields with no check

`judgment-apply.ts` sets `files.writeDeny.claudeCodeVersion = wd.claudeCodeVersion` and `files.toolExec.version = te.version` unconditionally. There is no type or semver check, no monotonic check, and no conflict rule. A delta can downgrade the version or set it to an empty string. That fails closed downstream, because no binary matches, but it is an unreviewed-looking overwrite. Exposure: assumption, so LOW. Test: **`JA-applier/version-field-validated`**.

### 7. [CLEAN][demonstrated] An uncertified binary never PASSes without its full judgment

The remedy is computed after every check, and status is `reasons.length === 0`. Certified only selects the remedy text and the flag. `CC-cert/uncertified-with-gap`, `CC-cert/versions-entry` and `CC-cert/obsolete-vscode-dir` pass (FAIL plus "prune" on a gap or another version). The only uncertified PASS is the judged version with a clean extraction, census included. **SURVIVES.**

### 8. [CLEAN][code-traced] `.obsolete` is writable by a session, or lists the active dir

### 12. [CLEAN][demonstrated] Question asked: are user-level `settings.json` and `ide` "already judged"?

No. They are genuinely different shapes, and the census comparison is correct. The window judges `settings.json` only in the **project** section (`.claude/settings.json`). The census's `(Se(),"settings.json")` is the config-dir getter (`var Se=cs(()=>(s()??i(R(),".claude")).normalize("NFC"),s)` on 2.1.267), which is `~/.claude/settings.json`, a user-level file. `unjudged()` compares `userAnywhere` against the union of `user` and `userOutsideWindow` only, by section, as it should. `~/.claude/settings.json` is already a named protected path (`src/qa/protected-path-list.ts:510`), so a2 only needs a `userOutsideWindow` entry pointing at it. `ide` is not in either window list, so `user:ide` (2.1.267) is genuinely unjudged. On 2.1.289 it disappears from the user census (finding 1) and survives only under the misleading project label (finding 2).

## Scariest unproven assumption

That the census is the completeness instrument for a2. It is a regex over minified shapes, and minified shapes drift between releases: `ide` moved from `mxe(Se(),"ide")` to `let e=we();_m(e,"ide")` between 2.1.267 and 2.1.289. A drift like that silently removes names. **Single next action:** add `CC-census/call-and-variable-base` and `CC-census/home-rooted-project-shape` (red), widen the project base pattern and add a home-root flag, then re-run the probe above against 2.1.289 and confirm `agent-memory`, `agent-memory-local` and `ide` (user) surface.
