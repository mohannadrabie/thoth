## Attacks, ranked by exposure x irreversibility x silence

### 1. One judged version against seven binaries at six versions: the CC row cannot pass on the operator machine. BREAKS. [MED][demonstrated]

Assumption: once #463 re-judges, the CC row turns green. Broken. The judgment carries one claudeCodeVersion string (src/qa/claude-code-write-deny-extract.ts:134), and checkOne fails any binary whose version differs (line 216). The delta now checks every versions/ entry and both Desktop bundles. This machine holds 2.1.240, 2.1.251, 2.1.267 (twice), 2.1.284, 2.1.286 and 2.1.289 (E4). The extracted lists genuinely differ across versions: 2.1.240 carries .config.json and .credentials.json and lacks seed-admin, while 2.1.286 and 2.1.289 add localSettings and projectSettings. No single judgment, at any version, matches them all.

Production trigger: the human finishes #463 (re-judge at 2.1.289) and runs readiness. It still prints FAIL on 2.1.240, 2.1.251, 2.1.267 (local-bin and versions), 2.1.284 and 2.1.286. Every failure line says "re-run extraction, re-judge every new entry, then bump claudeCodeVersion". For five of them that is the wrong remedy: re-judging cannot fix a version that is not the pinned one. The real remedies are human-only, and partly outside the human's control:
- Delete the retained versions/ entries. The native installer kept three (Aug 22, Aug 29, Sep 9). The dir is now protected, so only the human can delete them.
- Update the standalone CLI to the judged version.
- Delete the older bundle Desktop retained, then wait until Desktop bundles exactly the judged version. Desktop and the VS Code extension update on independent schedules, so this is a race; the alternative is uninstalling Desktop.

Is checking every entry correct fail-closed? Partly.
- Desktop bundles: yes. Desktop can open a local folder and run a Claude Code session in it, so its binary is one a governed session might run.
- Obsolete versions/ entries: no. The binary that runs is the local-bin one, which is already checked. A retained versions/ entry runs only if someone names it, so checking it adds failures with no added coverage.
- Obsolete extension dirs (VS Code marks them in its .obsolete file): the same story, but the round-2 downgrade case is real, because VS Code activates whatever its extensions.json names.

My round-2 finding 2 asked for the downgrade case to fail, which motivated "every entry". The versions/ half of that was over-broad.

Current defense: the CLI-drift paragraph of the runbook (docs/runbooks/k-kill-switch-and-verification.md:23) says only "re-vendor and re-judge (Issue #463)". Line 21 still says "the newest versions entry, the newest VS Code ... extension binaries", which is stale.

Exposure: 1 of 1 operator machine, 100% of readiness runs (7 binaries, 6 versions), basis: measured (E4). The failure is loud and reversible, not silent, so MED. The risk is the response it invites: a permanently red row pressures someone into an ignore list or a hand-bumped pin.

Required (one failing test): "CC-extraction-covers-judged/multi-version-judgment: two installed binaries at two different judged versions both PASS", meaning a judgment per version, or a list of judged versions each with its own extraction. Plus one of:
- (a) check versions/ entries only when local-bin is absent, or only the entry local-bin matches; or
- (b) a per-reason remedy in the FAIL line ("not the active binary: delete it" versus "re-judge"), and a runbook line naming the Desktop alignment constraint.

The implementer and Manager choose. Issue filed (see Issues).
