## Restated story

The `finally` cleanup in `src/secret-scan/pre-commit-scan.test.ts` uses a bare `rm(dir, { recursive: true, force: true })` and loses a race with a git process that writes into the temp clone after the test's `git commit` returned; the test fails with `ENOTEMPTY … .git/objects/info/commit-graphs` on the Linux runner. Fix it test-side only, keep every assertion, and keep persistent failures loud.

## Evidence that stands in for the un-reproducible race (rule 18: measured, not assumed)

The race cannot be reproduced here (Windows, Node 24.15.0, git 2.54.0; the runner is ubuntu-24.04, Node 22.18.0, git 2.55.0). What was measured instead, in a scratchpad, before shaping the plan:

| # | Measurement | Result |
|---|---|---|
| S1 | Trace (`GIT_TRACE=1`) of a successful `git commit` in a `git clone --local` of this repo | Default clone: git spawns `git maintenance run --auto --quiet --detach` after the commit. Clone made with `-c gc.auto=0 -c maintenance.auto=false`: no such process. Both keys persist in the clone's `.git/config` (`git config --local --get` returns `0` / `false`). A commit refused by the pre-commit hook does not reach that step, which matches the issue (only the `noprepare` test flakes; only it does a successful commit in the real-repo clone). |
| S2 | Concurrent-writer injection into a real directory tree shaped like `.git/objects/info/commit-graphs`, Node `rm` | Bare `{recursive, force}`: 31/40 ENOTEMPTY (300 ms wall-clock writer); 34/40, 32/40, 36/40 with a count-bound writer of 50, 200, 500 files. With `maxRetries: 5, retryDelay: 100`: 0/40 in every one of those four configurations. |
| S3 | CI base rate, last 60 runs (`gh run list` + step conclusions + `--log-failed` grep) | The Test step executed in 40 runs (22 success, 18 failure). ENOTEMPTY appears in exactly 1 of the 18 failures (run 35429687546). Observed flake rate 1/40, n = 1 event. |
| S4 | Site inventory, generated by grep (`\b(rm\|rmSync\|rmdir\|rmdirSync)\s*\(` over `src hooks scripts .githooks`) | 6 sites in the target file (lines 34, 194, 218, 225, 239, 272), 4 `mkdtemp(` calls. 29 more sites in 13 other files (see Residuals). |

**Stated limits.** S1 to S3 are from Windows/Node 24; Node 22 on Linux is not measured. The inference "the detached maintenance run is the writer" rests on the failing path (only git's gc/commit-graph code creates that directory) plus S1; it is not a captured trace from the runner. The retry schedule's total wait to exhaustion is NOT measured (a persistent-writer attempt succeeded after 123 ms instead of failing), so no criterion relies on a time budget.

**What is not promised.** No "N consecutive green CI runs" criterion. At an observed rate of 1/40, zero failures in n runs bounds the rate below about 3/n (rule of three, arithmetic): under 2.5% needs roughly 120 runs, which this project cannot collect for one Issue. After merge the Manager may report the measured count ("Test step ran k times, ENOTEMPTY seen j times"); that is an observation, not an acceptance criterion. "master CI green" is also not a criterion: QA-14 (Issue #229) stays red regardless.

## Design decisions (D1 to D4; each is vetoable, none blocks)

- **D1. One shared helper in a new module, not inline.** `src/lib/remove-tree.ts` exports `removeTree(dir, rmImpl = rm)`; it calls `rmImpl(dir, { recursive: true, force: true, maxRetries: 5, retryDelay: 100 })` and adds no catch, so exhausted retries still reject. Reason: the helper and the guard need tests, and adding tests to `pre-commit-scan.test.ts` would change that file's test count (13 today) and R3; the other 13 files in S4 can adopt the helper later as a mechanical swap. **Flag: this is a new module** (a reason-to-change of one line; used only by tests). Fallback if vetoed: inline the helper in `pre-commit-scan.test.ts` and keep only G-1 as a new test in that file (count 13 → 14, and HR tests are lost).
- **D2. Include R2, on the `noprepare` clone only.** Add `"-c", "gc.auto=0", "-c", "maintenance.auto=false"` to that one `git clone` (line ~226). Reason: R1 retries mask the race for an unmeasured duration; R2 removes the cause (S1) and stops a detached git process outliving the test. Two arguments, no assertion touched. Not applied to the first R4 test: its commit is refused by the hook, so no maintenance runs, and its title claims "no manual `git config` beyond that". R2 has no permanent test (a source-text assertion on a defense-in-depth argument would be brittle); its evidence is S1, recorded here and in the PR. If R2 is dropped, R1 alone still satisfies the Issue ("and/or").
- **D3. Line 194 goes through the helper too.** Verified by reading: it removes an empty directory that `mkdtemp` just created, before any git process exists, so no race is possible there. It is still routed through `removeTree` so the guard has zero exceptions (one rule, no carve-out list). Behavior is identical when nothing fails.
- **D4. Guard scope is one file.** G-1 covers `pre-commit-scan.test.ts` only, via a `GUARDED_TEST_FILES` array; the follow-up story appends each file it migrates. A repo-wide ratchet is not built now (rule 12).
