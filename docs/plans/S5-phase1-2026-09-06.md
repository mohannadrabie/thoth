## ADR Review

**ADR-0021 (Thoth-native architecture) — APPLICABLE, in full.** Unchanged from v1, plus one new confirmed boundary relevant to item 5:

- The in-session hook gate is implemented only through Claude Code's documented `PreToolUse`, `UserPromptSubmit`, `SessionStart`, `SubagentStop` primitives (ADR-0021 line 210, a closed list — "**MUST** implement... using only" these four, not "at least these four"); `SessionStart` alone cannot halt a session — the halt point is `UserPromptSubmit` (gap G5).
- The hook calls S2's `decide()` directly — one kernel build artifact, no second decision path (POL-03).
- The hook script is the impure shell; it imports the kernel, the kernel never imports it (POL-11).
- No new normalizer is added by editing a shared dispatch chain or the kernel (POL-12) — S5 calls the existing registry.
- The normalizer never verdicts; the kernel never inspects a tool's identity/shape directly (§3.2) — the hook does the `tool_name → toolType` mapping, and (v2 addition, criterion 19) does so as a fail-closed check inside the hook itself, not only via `.claude/settings.json`'s matcher string.
- No `@microsoft/agent-governance-*` import anywhere in S5.
- **New for v2:** Claude Code documents a fifth hook event, `ConfigChange` ("fires when a configuration file changes during a session," matcher sources `user_settings`/`project_settings`/`local_settings`/`policy_settings`/`skills`, capable of blocking a `project_settings` change per `code.claude.com/docs/en/hooks`) that would be a real, off-the-shelf way to react to a mid-session `.claude/settings.json` edit — the exact gap design-challenger's attack #5 names. **It is not used in this plan.** ADR-0021's line 210 closes the primitive list to exactly four; wiring `ConfigChange` would be an ADR violation, not a code fix, and amending an ADR is not this role's call mid-plan. Named explicitly (criterion 17) and routed to `architecture-reviewer`/a future ADR-amendment discussion, not built silently and not guessed at.

No other ADR (devops or software-engineering) governs this diff surface.

### Spike (T11, REVISED — fixes design-challenger attack #1 / Issue #86)

1. Corpus: S4's shell fixture/mutation corpus + explicit worst-case constructions (depth-cap-5 wrapper nesting, long multi-target commands) — unchanged from v1.
2. **Informational only, not load-bearing:** measure `normalize("shell", raw)` + `decide(worldFacts, action)` wall-clock in-process (`process.hrtime.bigint()`, ≥1000 iterations) → p50/p95/p99. Kept for visibility into the pure-function cost alone; **explicitly not used to derive the declared timeout** (this was v1's defect).
3. **The real measurement:** `spawnSync("node", ["hooks/pretooluse-kernel-gate.mjs"], { input: <realistic stdin JSON>, encoding: "utf8" })`, run **≥30 times**, each a fresh cold process (no loop-reuse), timed via `process.hrtime.bigint()` wrapped around each individual `spawnSync` call. Compute p50/p95/p99 of this subprocess wall-clock. Run on the actual target machine class (this repo's own dev/CI machine), not assumed.
4. Confirm Claude Code's own documented default command-hook timeout (600s absent an explicit `timeout` key) and that `timeout` is per-entry configurable with no documented ceiling below that default (unchanged from v1).
5. **Declared `timeout` = safety-margined multiple of the measured SUBPROCESS p99** from step 3 (never step 2's number) — record methodology + number in `docs/spikes/T11-timeout-budget-2026-09-06.md` + a `docs/decisions.md` row (T11, closed). This is the direct, named fix for Issue #86.
6. Regression test: assert the declared `timeout` in `.claude/settings.json` is ≥ a stated safety multiple of a freshly re-measured subprocess p99 — so a future change that silently shrinks the margin fails CI, not just this one-time spike.

- `src/qa/gate-command-path-check.ts` (**NEW**, criterion 13) — parses `.claude/settings.json`'s `hooks` object; for every `type: "command"` entry's `command` string, extracts the referenced script path, substitutes `${CLAUDE_PROJECT_DIR}` against the repo root, and asserts the resolved path exists on disk via `existsSync`.   ```json
  {
    "sessionId": "<uuid>",
    "reasons": {
      "SUR-03-unclassified-tool": { "set": true, "detail": "unclassified: mcp__foo__bar", "setAt": "<ISO-8601>" }
