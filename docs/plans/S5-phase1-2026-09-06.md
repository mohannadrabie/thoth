## ADR Review

**ADR-0021 (Thoth-native architecture) — APPLICABLE, in full. Unchanged from v2.**

- The in-session hook gate is implemented only through Claude Code's documented `PreToolUse`, `UserPromptSubmit`, `SessionStart`, `SubagentStop` primitives (ADR-0021 line 210, a closed list — "**MUST** implement... using only" these four, not "at least these four"); `SessionStart` alone cannot halt a session — the halt point is `UserPromptSubmit` (gap G5).
- The hook calls S2's `decide()` directly — one kernel build artifact, no second decision path (POL-03).
- The hook script is the impure shell; it imports the kernel, the kernel never imports it (POL-11). **This is also the basis for architecture-reviewer's council-seat ruling on Issue #89**: reading `~/.claude.json`/`.mcp.json` from a hook script crosses no kernel-purity or normalizer-registry boundary — hooks are already the documented impure shell, and no shipped kernel rule gates read-only access to a user's own home-directory config today. The risk that fix genuinely introduces is not the read, it's the new output surface for what gets read (criterion 16, below).
- No new normalizer is added by editing a shared dispatch chain or the kernel (POL-12) — S5 calls the existing registry.
- The normalizer never verdicts; the kernel never inspects a tool's identity/shape directly (§3.2) — the hook does the `tool_name → toolType` mapping, and (criterion 19) does so as a fail-closed check inside the hook itself, not only via `.claude/settings.json`'s matcher string.
- No `@microsoft/agent-governance-*` import anywhere in S5.
- Claude Code documents a fifth hook event, `ConfigChange`, that would be a real, off-the-shelf way to react to a mid-session `.claude/settings.json` edit — the exact gap design-challenger's round-1 attack #5 names. **It is not used in this plan.** ADR-0021's line 210 closes the primitive list to exactly four; wiring `ConfigChange` would be an ADR violation, not a code fix. Named explicitly (criterion 18) and routed to `architecture-reviewer`/a future ADR-amendment discussion, not built silently and not guessed at.

No other ADR (devops or software-engineering) governs this diff surface.

### T11 / SUR-12 / OPS-03 — split-budget model (REVISED per council ruling; replaces v2's single-derived-number section 5 in full)

**The council ruled this is two distinct numbers, in two distinct files, never derived from each other. Both are named concretely below.**

#### A. SUR-12's declared enforcement `timeout` — `.claude/settings.json`, fixed at 60 seconds

This is the actual value Claude Code's runtime enforces on the `PreToolUse` entry for `hooks/pretooluse-kernel-gate.mjs`. It is chosen directly — **not** derived from any measured invocation-latency figure — for two reasons, both concrete and both checked this revision (not assumed from memory):

1. **Precedent already shipped in this exact repo.** `.claude/settings.json`'s existing `report-subject-gate.mjs` entry (line 101, still present until criterion 15's removal lands in the same commit) sets `"timeout": 10` against a disclosed real cost of "approximately 50 small synchronous reads" — order of a few milliseconds, a >1000x margin, chosen once and never re-derived across four prior CRITICAL-tier review cycles. That is the working shape this value follows.
2. **Claude Code's own documented ceiling.** Re-confirmed this session (not assumed 600s from memory): Claude Code's Hooks reference (`code.claude.com/docs/en/hooks`) documents a **600-second (10-minute) default timeout for `command`-type hook entries**, including `PreToolUse`, configurable per-entry with no documented ceiling below that default. Evidence tier: `derived` (a live web search this session, not a raw page fetch I executed directly) — but convergent across multiple independent sources found this session, and consistent with what both `design-challenger` round 2 and `architecture-reviewer`'s council seat already confirmed via a **direct** fetch of the same page in their own reports (cited above). One community-filed doc-accuracy issue (`anthropics/claude-code#19175`, opened 2026-01-19) noted the reference had briefly under-documented this as 60s before a `v2.1.3`-era fix restored the correct 600s figure — checked and accounted for, not glossed over, since it's exactly the kind of stale-number risk this whole revision exists to avoid repeating.

**Chosen value: 60 seconds** — not the full 600s ceiling, and not a re-derivation from the measured p99. This follows architecture-reviewer's specific council-seat guidance (its ruling names "e.g. 30s or 60s" as the concrete band, `story-implementer`'s call with a one-line justification): 60s sits

- **comfortably below Claude Code's own 600s ceiling** — a genuinely wedged/hung process (an actual bug, not a slow machine) is still caught in bounded time, 10x tighter than the documented maximum, rather than blocking a user's whole session for up to ten minutes on a real hang; and
- **roughly 57x (~1.7 orders of magnitude) above the worst real invocation cost either `design-challenger` round has measured** (1051.2ms p99, PowerShell-fallback shell form, round 2) — comfortably within the "one to two orders of magnitude above worst-measured" band the architecture-reviewer's ruling specifies, with no dependency on that number ever being re-measured tighter.

This is a `story-implementer` judgment call, recorded once — the one-line justification above — in `docs/decisions.md` at build time, not re-derived under future review pressure. **This number does not come from, and is never checked against, the OPS-03 spike below** — that would silently reintroduce the exact one-number-two-jobs collapse the council ruled structural.

#### B. OPS-03's own latency budget — `src/qa/gate-latency-budget-check.ts`, CI-regression-tested, measured

This is a **separate** number, living in a **separate** file, whose only job is to catch drift in the gate's real-world performance — never to bound security exposure. Its overrun is a CI-10 incident (a red build, a human investigates), never a live bypass.

1. **Corpus:** S4's shell fixture/mutation corpus + explicit worst-case constructions (depth-cap-5 wrapper nesting, long multi-target commands) — unchanged from v1/v2.
2. **Informational only, not load-bearing, kept for visibility:** in-process `normalize("shell", raw)` + `decide(worldFacts, action)` wall-clock (`process.hrtime.bigint()`, ≥1000 iterations) → p50/p95/p99. Not used to derive anything.
3. **The real measurement, unchanged methodology from v2 (round 2's own fix was correct and is kept as-is):** `spawnSync` of the real `node hooks/pretooluse-kernel-gate.mjs` invocation, run ≥30 times, each a fresh cold process, timed via `process.hrtime.bigint()` wrapped around each individual call — through the **actual shipped entry shape** (a bare command string → real shell layer: `sh -c` / Git Bash / PowerShell fallback per platform), on the actual target machine class (this repo's own dev/CI machine), not assumed. Compute p50/p95/p99.
4. **Declared OPS-03 ceiling = a number set from step 3's actual measured corpus** — architecture-reviewer's council-seat ruling suggests "on the order of 1–2 seconds" as the target band; the exact figure is `story-implementer`'s call once the spike has actually run (build-order step 4 above), recorded with its own one-line justification in `docs/decisions.md`, separately from criterion 8's number. Until that spike runs, this plan commits to the **mechanism and the target band**, not a final digit — consistent with rule 17/18's "spike before shape" for a number the design genuinely depends on.
5. **`src/qa/gate-latency-budget-check.ts` (NEW):** same `InstrumentResult`/`printInstrumentResult`/`exitCodeFor` shape as every other `src/qa/*` check. Re-runs step 3's measurement against the corpus, asserts the freshly-measured p99 stays under the recorded OPS-03 ceiling. **A failure here is a CI-10 incident** (`REQUIREMENTS.md:468`'s own text: "a timeout occurrence is an incident under CI-10, not a routine event" — read correctly once "timeout" in that sentence means this budget crossing, not the enforcement ceiling firing) — it never silently changes, and is never wired to change, criterion 8's `.claude/settings.json` value. Wired as `qa:gate-latency-budget` in `package.json`/`ci.yml`.

**Stated explicitly, per the council's requirement:** the enforcement `timeout` (§A, `.claude/settings.json`, fixed at 60s, no measurement dependency) and the OPS-03 alarm budget (§B, `src/qa/gate-latency-budget-check.ts`, measured, CI-regression-tested, target band 1–2s pending the actual spike run) are **two different numbers in two different files/checks**, never conflated, never derived from each other. This is the direct, structural fix for Issue #86 the council ruled required.
