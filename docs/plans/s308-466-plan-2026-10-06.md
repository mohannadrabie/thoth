## 2. Findings that shape the design

- Roots in discovery (discoverClaudeBinaries in `src/qa/claude-code-write-deny-extract.ts`, lines 87-92):
  - classic: APPDATA (else ~/AppData/Roaming) /Claude/claude-code/ver/hash/claude(.exe)
  - MSIX: LOCALAPPDATA (else ~/AppData/Local) /Packages/Claude_*/LocalCache/Roaming/Claude/claude-code/ver/hash/...
  - Real folder on this machine, confirmed by ls: Claude_pzs8sxrjxfjjc. The ver/hash segments sit inside the root, so a directory-prefix entry covers them (no per-machine segment).
- How each root is expressed (canonical form: lowercase, ~/-relative, trailing / = directory; no new syntax):
  - ~/AppData/Roaming/Claude/claude-code/ (canonical ~/appdata/roaming/claude/claude-code/)
  - ~/AppData/Local/Packages/Claude_pzs8sxrjxfjjc/LocalCache/Roaming/Claude/claude-code/ (canonical ~/appdata/local/packages/claude_pzs8sxrjxfjjc/localcache/roaming/claude/claude-code/). Only the pinned publisher ID is listed. Discovery still enumerates every Claude_* folder, so a planted Claude_evil package is found and FLAGGED, not protected.
  - APPDATA/LOCALAPPDATA fallback: the list holds only the default-location form (same as every other ~/ entry). Discovery resolves roots from env APPDATA (else ~/AppData/Roaming) and LOCALAPPDATA (else ~/AppData/Local). If the env value is redirected somewhere not under a protected ~/ entry, the binary is unprotected and is flagged (fail-closed). No %APPDATA% syntax is added to the list. Disclosed limit: a human with a genuinely redirected profile gets a flag and uses the opt-in.
- Generator side effects (not typed by hand): new Edit(~/appdata/.../**) and bare-path entries in the K proposal, deny rules in `src/policy/config/shipped-defaults.json`, and parent-dir move/delete/rename denies for ~/appdata, ~/appdata/roaming, ~/appdata/roaming/claude, ~/appdata/local, ~/appdata/local/packages and the deeper parents. Disclose in the PR: a session cannot move, delete or rename ~/AppData/Local/Packages. Mixed-case Edit matching on Windows is the already-carried P-K4 spike, not new.
- One source for "unprotected": protectedPaths(root).all filtered to ~/ entries. New pure function in a NEW module, src/qa/unprotected-location.ts (plain text, does not exist yet): classifyLocation(absPath, home, protectedAll) returns "protected" or "unprotected". It rewrites a path under home to ~/..., applies canonicalizePathTarget, and is protected iff some ~/ entry equals it or is a directory prefix of it. A path outside home is unprotected. It checks BOTH the discovered path and its realpathSync; protected only if both are (a junction cannot launder a path in). No second hand list. Import direction: extract imports protected-path-list; the latter does not import the former (checked), so no cycle.
- Existing protected install dirs stay protected: ~/.local/bin/, ~/.local/share/claude/, and the three extensions/ dirs. Unprotected by this rule: absolute PATH entries not under those, the THOTH_CLAUDE_BIN override outside them, Desktop roots under a redirected profile, unpinned Claude_* packages.
