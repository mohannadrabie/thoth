## 3a. Confidence path for the real registry channel before ship (NEW — design-challenger Attack A)

Neither this session, nor `design-challenger`'s own independent attempt this round, nor any CI run (`ubuntu-latest`, no `HKLM` exists there) can execute a real `reg query` against `HKLM\SOFTWARE\Policies\Thoth`. This is not a gap this plan can code its way out of — it is a structural property of the environments every agent session in this project runs in. The confidence path is therefore layered, and each layer's limit is stated plainly rather than papered over:

1. **Outbound call-shape confidence (automatable, CI-safe):** AC7's existing mocked-`child_process` test asserts the exact arguments `central-source.ts` passes to `reg query` (key path, value name, no shell interpolation of either) — this proves the call is well-formed and injection-safe, but proves nothing about what comes back.
2. **Inbound parse confidence (automatable, CI-safe, NEW this revision):** AC7 is extended with a unit test for the stdout-extraction routine against a **literal, human-captured fixture** of real `reg.exe query` output (the actual multi-line, indentation-padded, `REG_SZ`-tagged tabular format `reg.exe` emits — not a hand-guessed approximation of it). This closes the gap design-challenger's Attack A named: AC7 as originally written only tested the outbound call shape, never the inbound parse.
   - **Owner: a human**, on a real (non-agent-sandboxed) Windows shell, one time, before Phase 2 build's `central-source.ts` task is considered done. No agent session in this project's history — this one, or design-challenger's independent attempt this round — has been able to run `reg` commands; both attempts were denied by Claude Code's own tool-permission classifier before reaching the OS. This is disclosed as a structural limit, not a missed step.
   - The captured fixture ships as a committed test asset (`docs/qa/s6-policy-loader-fixtures/real-reg-query-output.txt` or similar), so the human-in-the-loop step happens exactly once, not on every CI run thereafter.
3. **Full end-to-end confidence (manual, one-time, before Stage 3 review closes):** the human owner also runs the shipped `policy:print` command directly against a real `HKLM\SOFTWARE\Policies\Thoth` value they provision by hand on this machine (or another real Windows machine), once, and the raw output of that run is captured into the Stage 3 review evidence. This is the only way any confidence reaches the full real path (registry write → `reg query` → parse → merge → print) before ship, given no agent sandbox can do it. If this manual run is skipped, Stage 3 review must say so plainly (PRINCIPLES rule 13 — never skip a gate silently) rather than let AC7's automated tests stand in for it.
4. **Documented, not hidden, blind spot:** a one-line doc comment on `central-source.ts` states this exact limitation (CI cannot exercise the real channel; no agent sandbox in this project's history has been able to either) so a future reader doesn't assume AC7's automated tests cover more than they do.
5. **Write-ACL claim stays disclosed exactly as v1 left it** (vendor-doc-cited + documented Windows `HKLM\SOFTWARE` default ACLs, not personally measured — UAC token-filtering is a real, named caveat on top of that, per design-challenger's Attack A, and is folded into the same doc-comment disclosure in (4), not overclaimed as resolved).

## 4a. Flagged residual requiring a human call (NEW — design-challenger Attack C, architecture-reviewer finding 6)

**The tension, stated plainly, not resolved here:** the 2026-09-08 ruling explicitly chose "build the general form, test central→project only." Both reviewers independently name the same concrete risk in that choice: `mergeLayersWithMandatoryLock`'s general-form check can be implemented two ways — one correct for any layer pair (inspects the stored rule's own `mandatory` field), one plausible-but-wrong (inspects which layer produced it, e.g. `sourceLayer === "central"`) — and the two are **indistinguishable by the ratified central→project-only test suite**. This codebase has shipped exactly this failure shape before, one layer deeper each time (Issues #65/#66, #99 — "the check that looks equivalent for the tested case isn't equivalent for the general case"). Current exposure is honestly 0% (`shipped-defaults.json` ships as an empty `rules: []` placeholder this story, per the content-authoring-out-of-scope ruling — there is no real mandatory shipped-defaults rule to fail to protect yet), but the risk is latent, not absent: the moment a future content-authoring story adds a real mandatory shipped-defaults rule, this exact code path activates with no review of S6's own precedence mechanism scheduled at that point.

design-challenger frames its proposed proof-test (one `precedence.test.ts` case: shipped-defaults marks a rule `mandatory: true`, central attempts to redefine it, asserted rejected) as **additive engineering hygiene, not a reopening of the ratified scope** — an internal regression test pinning the general mechanism's own correctness, distinct from AC1's ratified central→project acceptance criterion. architecture-reviewer, seeing the same gap, recommends the lighter disposition: a `docs/backlog.md` line only, owned by the future content-authoring story, since the ruling already settled the scope question.

**Two options, not a recommendation forced on the human:**
- **(a) Add the second test now.** Cheapest moment to write it (the code is fresh in review context this story); costs one more `precedence.test.ts` case; does not reopen or expand the ratified central→project scope, only adds a regression pin alongside it.
- **(b) Keep the original ruling as-is and backlog it.** Matches architecture-reviewer's lighter read (0% exposure today, latent not live) and the ruling's own stated intent (test only the ratified direction); defers the cost to whichever future story first sets `mandatory: true` on a shipped-defaults rule.

**This plan does not pick between (a) and (b).** The Manager carries both options, with both reviewers' reasoning, to the human as part of this v2's approval gate. Whichever is chosen, it is recorded as its own `docs/decisions.md` row before Phase 2 build starts (same convention as every other S6 design ruling this story has already used) — not left implicit in a test's wording, which is exactly the failure mode Attack D (§ below, AC9) independently flagged for a different part of this same mechanism.

## 8. Plan

**Build task #1 (walking skeleton, rule 17):** unchanged from v1.

**New files** (unchanged from v1, plus explicit naming below):
- `src/policy/config/central-source.ts` — `CentralPolicySource` interface + default Windows-registry reader. **Interface return shape, named explicitly (architecture-reviewer findings 2 + 4, folded into one fix):**
  ```ts
  type CentralPolicyResult =
    | { status: "absent" }                                   // channel checked on this platform, nothing deployed
    | { status: "unsupported" }                               // no reader implemented for the current platform
    | { status: "present"; raw: string; channel: string };    // e.g. channel: "win32-registry:HKLM\\SOFTWARE\\Policies\\Thoth\\CentralPolicyJson"

  interface CentralPolicySource {
    read(): CentralPolicyResult;
  }
  ```
  A discriminated union, not a bare nullable — `"absent"` (channel mechanism ran, confirmed nothing there) and `"unsupported"` (no reader exists for `process.platform` at all) are structurally distinct return values, so a future non-Windows build cannot silently collapse "unsupported platform" into "no policy" (the fail-open-reads-as-fail-closed risk architecture-reviewer's finding 2 named). `channel` is a free-form descriptor string, not a Windows-specific field, so a future macOS/plist reader is an additive second implementation of the same interface, not an interface change.
- `src/policy/config/position-parser.ts` — minimal line/column-tracking JSON tokenizer (no new dep). **`position-parser.test.ts` named explicitly** (v1 only implied this via "test files for every module above"; design-challenger's Attack E treats its absence as a real gap).
- `src/policy/config/loader.ts` — `loadEffectivePolicy()`: reads all three tiers, validates, mandatory-locks, pins, merges. **Single-read invariant, named explicitly (design-challenger Attack F, AC2):** the central channel is read exactly once per invocation; the same returned bytes feed both the merge and the pin computation. If a future refactor needs more than one logical read, the pin MUST be computed over exactly the bytes that were actually merged, never a second independent call to `CentralPolicySource.read()`.
- `src/policy/config/pin.ts` — SHA-256 content-hash + channel-descriptor + timestamp. Unchanged from v1 except it now explicitly takes the already-read bytes as an argument (never re-reads the channel itself) — enforces the single-read invariant above at the type level (no `CentralPolicySource` dependency in `pin.ts` at all).
- `src/policy/config/printer.ts` + a runnable entry (`npm run policy:print` or similar) — POL-10. Unchanged.
