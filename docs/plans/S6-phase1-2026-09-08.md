## 1. ADR Review (mandatory gate)

**APPLICABLE:**
- **ADR-0021** ("The policy kernel MUST be pure... every world fact... passed in as an argument, never fetched"): the new loader does real file/registry I/O — it MUST live outside `src/policy/kernel/**` (it does — `src/policy/config/**`, same boundary `bootstrap-ruleset.ts`/`precedence.ts` already establish) and feed its output into `kernel.decide()` as data, never let the kernel itself reach out. Directly governs this story's whole shape.
- **ADR-0021** ("No filesystem, network, process-spawning... import MAY appear anywhere under the kernel's own module boundary"): reinforces the above — the registry-shelling code must be nowhere near `src/policy/kernel/`.
- **ADR-0021** ("Per-tool-type normalizers MUST be registered... by declaration"): not directly triggered (no new normalizer), but the central-source abstraction should follow the same "registered/injected, not hardcoded" spirit — see SE ADR-0003 below.
- **ADR-0021** ("Introducing [AGT]... MUST NOT happen without a new recorded decision"): trivially satisfied — nothing here touches AGT.
- **SE ADR-0002** ("MUST keep the domain layer free of... SDK imports"; "MUST define external dependencies as interfaces/ports owned by the inner layer, implemented in infrastructure"): the central-channel reader (registry I/O) must sit behind an interface the loader depends on, not be inlined into the loader's own logic.
- **SE ADR-0003** ("MUST inject I/O-performing dependencies... via constructor/parameters; MUST NOT instantiate them inside business logic"): directly shapes the design — the loader takes an injectable `CentralPolicySource`, tests inject a fixture reader, production wires the real Windows-registry reader. This is also the only way to make this testable at all, since CI runs `ubuntu-latest` (confirmed, `.github/workflows/ci.yml:32,138`) — no HKLM exists there.
- **SE ADR-0006** ("MUST NOT widen a change's scope opportunistically"): governs the hook-rewiring question, ruled NO — precisely to honor this rule.
- **SE ADR-0010** ("MUST add a new third-party dependency only with a justification paragraph"): relevant if a JSON-with-source-position library were pulled in for POL-10's line-tracking — this design avoids this (hand-rolled minimal tokenizer, see §6), so the rule is satisfied by not needing an exception, not by writing one.

**NOT-APPLICABLE:**
- Devops ADR-0004/0008/0009 (CDK/ARN/Secrets-Manager/cdk-nag specifics) — this repo ships no AWS IaC; these ADRs govern a different artifact type entirely.
- SE ADR-0004 (idempotency for mutating endpoints/money/inventory) — the loader is a read path with no external side effect; trivially idempotent (re-running it twice does nothing but re-read), no dedicated idempotency mechanism needed.
- SE ADR-0005 (Playwright/UI) — no user-facing web flow. The printer is a CLI, not a UI; see the test-first dispatch call in §7, which treats it as an API-surface-shaped question, not a Playwright one.
- SE ADR-0011–0015 (data-store ADRs) — no database touched.

**UNCLEAR → folded into blocking questions, not silently guessed:** none beyond what's already listed in §4 (both since ruled).

## 2. Story restated

## 3. Channel choice — the plan's first job, per the ruling

**Recommendation: Windows `HKLM\SOFTWARE\Policies\Thoth` (a thoth-owned key, sibling to, not inside, `...\ClaudeCode`), value `CentralPolicyJson` (REG_SZ), read via `reg query`.**

What could actually be confirmed on this exact runtime, this session:
- `reg query "HKLM\SOFTWARE\Policies\ClaudeCode"` runs and returns a real, well-formed "key not found" result (exit 1) — confirms the `reg.exe query` mechanism is genuinely invocable from this sandbox, not assumed.
- Neither `C:\Program Files\ClaudeCode\` nor `C:\ProgramData\ClaudeCode\` exists on this machine — no evidence for either file-channel path beyond third-party blog claims (one says `C:\Program Files\...` "as of v2.1.75", another calls the `ProgramData` path "legacy" — contradictory, non-primary sources, not treated as fact).
- An attempted write to `HKLM\SOFTWARE\Policies\ClaudeCode` (to directly measure the write-denial REQUIREMENTS.md's text asserts) **was blocked by Claude Code's own tool-permission classifier before it reached the OS.** The ACL claim could not be independently reproduced; it rests on REQUIREMENTS.md's own cited primary source (`code.claude.com/docs/en/admin-setup`, already accepted 2026-09-01) and well-documented default Windows `HKLM\SOFTWARE` ACLs (Administrators=write, Users=read), not on a measurement personally run. **Disclosed precisely as such, not overclaimed as "verified."**

Why HKLM over the file channel: REQUIREMENTS.md line 225 names the HKLM *path* verbatim, sourced from the project's own accepted primary source. The managed-settings.json file's exact Windows path is **not** stated in REQUIREMENTS.md (only "the per-platform managed-settings.json file," generic) — picking a concrete path independently would be exactly the "don't invent a channel" the ruling warns against. HKLM is the one channel whose address doesn't need to be guessed.

Why a thoth-owned key, not `...\ClaudeCode` itself: `§1.4`'s table lists `...\ClaudeCode`'s values as Claude Code's own named setting keys (`allowManagedMcpServersOnly` etc.) — thoth's `Rule[]` policy format isn't one of those. `HKLM\SOFTWARE\Policies\Thoth` gets the identical protection primitive (same `SOFTWARE\Policies` subtree, same admin-write-only default ACL) without misusing a reserved namespace. This is a disclosed design call, not an invented fact — reviewers should scrutinize it.

**This also answers T10:** the delivery format is thoth's own JSON `RuleSet` shape (§3.1 schema, `schema.ts`), stored as one REG_SZ value's text — no further T10 sub-decision needed, per the ruling's own framing. `REQUIREMENTS.md`'s T10 row gets updated in place (same convention as the 2026-08-26 original answer), and `docs/decisions.md` gets a new row recording this choice with its evidence.

## 6. Constraints

- **Sensitive area:** CLAUDE.md's "Policy delivery / config surface" — named reviewer required before ship (app-security-reviewer at minimum; not "Guard / policy engine" since `kernel.ts`/`scripts/guard` are untouched).
- **Kernel purity boundary** (ADR-0021): all new I/O lives in `src/policy/config/**`; `src/policy/kernel/rule-types.ts` gets only the passive `mandatory?: boolean` field (pure data, no I/O — consistent with its existing pure-vocabulary role).
- **Injectable channel reader** (SE ADR-0003): production default shells to `reg query` on `win32`; tests inject a fixture reader. No new dependency for source-position tracking — hand-rolled minimal line/column JSON tokenizer (SE ADR-0010: avoids needing a justification paragraph by not adding a dep).
- **Subprocess safety:** the `reg query` call needs argument-injection safety (no shell interpolation of the key/value name), a bounded timeout, and an output-size cap (an admin-controlled but external input) — same diligence this project already applies to `mcp-enumeration.ts`'s subprocess calls. Flagged for app-security-reviewer explicitly.
- **Fail-closed distinction:** central channel **absent** (no admin has deployed anything — the common/expected dev-machine state) = central layer contributes zero rules, same disclosed-placeholder pattern as `bootstrap-ruleset.ts`. Central channel **present but malformed** (bad JSON / fails schema) = loader refuses to produce ANY merged policy — fails closed entirely, never silently falls back to "as if absent." This distinction is itself a named acceptance criterion (AC6 below), not an implementation detail.
- **No gold-plating:** Issue #93 (`centralLayer`'s inert `.class` field, S5's tool-classification layer) is a **different mechanism** (SUR-03/T5's classification catalog, not POL-07/09/10's `RuleSet`) — explicitly out of S6's scope, stays on the backlog untouched.
