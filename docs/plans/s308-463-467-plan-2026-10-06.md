## 6. Plan

### 6.1 a1 (buildable now, no human input)
1. **Certified-set definition in one place**: in `src/qa/claude-code-write-deny-extract.ts`, discoverClaudeBinaries returns FoundBinary with new certified: boolean and uncertifiedWhy?: string, set by one function classifyBinary(...). Rules:
   - uncertified = a versions/ entry whose path is not also the local-bin binary, or an extension dir (vscode, vscode-insiders, cursor) listed in that editor's extensions/.obsolete file (a JSON object keyed by dir name; assumed VS Code format, not present on this machine today).
   - certified = every other discovered binary: local CLI, non-obsolete extension dirs, Desktop bundles, absolute PATH entries and the THOTH_CLAUDE_BIN override (anything launchable by name or explicitly requested). The PATH/override/Cursor/Insiders reading is accepted by Manager ruling 2.
   - A missing .obsolete file means no extension dir is obsolete. An unreadable or invalid .obsolete fails closed: every extension dir is certified, plus one reason line naming the file.
2. **Per-binary remedy in checkOne**:
   - certified, version differs from the judged one: FAIL, remedy "update to <judged version>, or remove it (Desktop: bundle <judged version> or uninstall)".
   - certified, version matches, extraction gap: FAIL, remedy "re-judge" (the existing text).
   - uncertified, version matches and the extraction is clean: PASS.
   - uncertified, version differs or extraction gap: FAIL, remedy "prune: delete <path>" (never "re-judge").
   - Stale entries stay FAIL until the human prunes them, matching the ruling that the human deletes them.
   - BinaryResult gains certified and remedy. The final line marks each binary certified|uncertified and shows its remedy, because the readiness row's detail is the final line only (`src/qa/k-readiness.ts`, scriptRow).
   - Builds on c's extract.ts changes: c's exec gate means the --version call only runs for binaries in protected dirs; a1's remedy logic must handle a binary whose version was not asked (the gate declined), and the builder reconciles this against c's final code.
3. **Census for the out-of-window shapes** (#463 acceptance addition, so the human's extraction paste is complete): extractWriteDeny also returns userAnywhere and projectAnywhere, using the same two shape regexes over the whole binary (not the anchored window). The CLI prints them. checkOne fails any name in the census that is neither judged nor listed in the new judgment section (6.1.4) as "census unjudged: ...". The census is a superset check only (no judged-in-census-but-absent direction). Memory: whole-binary latin1 scan of a ~200 MB file, bounded by scanning in chunks with an overlap of at least the longest shape; the builder measures runtime and states it.
4. **Judgment schema section for sites outside the extractor window**: the write-deny judgment file gains projectOutsideWindow and userOutsideWindow arrays (same JudgedEntry shape), exempt from judgedNotExtracted but included in the unjudged census check and in the CC-protected-entries-on-the-list loop. The Judged type and the structure test are extended to match. This is where CLAUDE.md, rules, .git, ide, worktrees and dev-mods go.
5. **Judgment applier (Q1 ruled: build it)**: src/qa/judgment-apply.ts (new file) plus npm script qa:judgment-apply. Input: a committed approved-delta file (docs/qa/judgment-deltas/s308-463-467.json, new file: version bump, entries to add with judgment/reason/path, for both judgment files). Output: re-serialized judgment files. It refuses an existing entry with a different value, an unknown judgment value, and a duplicate; running it twice gives a zero diff. The delta file is the human-approved record, so judgments never change by hand edit.
6. **Tests written failing first** (in `src/qa/claude-code-write-deny.test.ts` unless stated), each a named check:
   - CC-cert/certified-with-gap: certified binary, one unjudged entry, FAIL, remedy contains "re-judge".
   - CC-cert/uncertified-with-gap: a versions/ entry with a gap, FAIL, remedy "prune", text does not contain "re-judge".
   - CC-cert/uncertified-clean: a versions/ entry at the judged version, clean extraction, PASS.
   - CC-cert/obsolete-vscode-dir: two extension dirs, one listed in .obsolete: obsolete = uncertified, FAIL "prune" on a mismatch, active = certified.
   - CC-cert/versions-entry: versions/<v> at a different version, FAIL "prune"; same bytes as the local-bin binary at the judged version, PASS.
   - CC-cert/certified-version-mismatch: local CLI at another version, FAIL "update", not "prune".
   - CC-cert/obsolete-file-invalid: malformed .obsolete, every extension dir certified, reason names the file.
   - CC-cert/single-definition: a test greps source for the certified rule outside classifyBinary and fails if a second definition appears.
   - CC-census/*: a fake binary with an out-of-window (x,".claude","ide"): reported in projectAnywhere, FAIL as unjudged, PASS once judged.
   - Existing 2.1.267-based tests keep passing (no .obsolete file means all extension dirs certified, so every-entry-not-newest-only still holds).
   - JA-applier/* (src/qa/judgment-apply.test.ts, new file): idempotent, refuses a conflicting overwrite, refuses an unknown value, mutant (drop an entry) caught.
7. **a1 verification**: npm test for the touched test files with real counts, npm run qa:cc-extraction-covers-judged (its result on this machine is still FAIL until the human prunes; a1 reports that as the expected, named remedy output, not a pass claim), typecheck, lint, qa:protected-path-list (drift check) and npm run qa:k-readiness (reported, not required green). All commands with timeouts.
